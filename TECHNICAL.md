## Constraints that shape everything

Darsi's users are teachers on low-cost Android phones, often shared, with expensive and patchy mobile data, limited battery and little free storage. Most technical choices below follow from four rules:

1. **Offline is normal.** The app must open and teach with no signal. The network is an optimisation, never a requirement.
2. **Light on data and battery.** There are no live Firestore listeners and no polling, with one exception: AuthProvider listens to the signed-in person's own profile, so a role or organization change reaches the phone (see Roles). Staff screens (`admin/data.ts`) read once when they open, again after their own changes, and on Refresh. The app does one read per sign-in and writes only what changed. Heavy code is lazy-loaded, sizes are shown before downloads, and nothing autoplays.
3. **Every language is a first language.** Arabic (RTL) and English are both first-class. Layout uses logical CSS properties only, and numbers follow the locale.
4. **One codebase, three targets.** The PWA is the app. Capacitor wraps the same build for Android and iOS. Only `src/platform/` knows whether it runs in a browser or a native shell.

## Commands

Run from the repository root. Node 22 is recommended and npm 11 is expected (`npx -y npm@11.13.0 install` if npm 10 fails).

| Command | What it does |
|---|---|
| `npm install` | Installs the workspaces and builds the design system |
| `npm run dev` | Dev server at http://localhost:5173, talking to the Emulator Suite (`.env.development`) |
| `npm run build` | Builds the design system and the PWA into `apps/web/dist` (uses `.env.local`, the real project) |
| `npm run preview` | Serves the production build at http://localhost:4173 with the service worker on |
| `npm test` | Unit tests (design system + app) |
| `npm run e2e` | Playwright on desktop and phone. It runs `npm run build` first and serves that build on its own port, 4180 (`E2E_PORT` for another); it never reuses a server already there, so a busy port fails the run. Set `CHROMIUM_PATH` if Playwright's own Chromium isn't installed |
| `npm run typecheck` | TypeScript across the workspace |
| `npm run lint:css` | Checks every app stylesheet against the RTL, token and old-WebView rules |
| `npm run kits` | Regenerates the classroom kits in `content/kits` from `content/units` |
| `node scripts/import-packs.mjs --packs <dir> --studio ../lessonstudio` | Imports the unzipped course packs as units (English), with their videos and light lessons from Lesson Studio in `content/media`. An existing unit file is left alone unless `--force`; `--media-only` refreshes only the video fields and files |
| `npm run seed -- --emulator` | Publishes the course sources (`content/units`) to the emulators; without `--emulator`, to the real project (Application Default Credentials, as for `superadmin`). Name the units (`npm run seed -- <id>…`); with no ids it takes every file there. An existing draft is left alone unless `--replace`. **On the live project, never `--replace` without ids:** it would republish all 96 sources, including the courses deliberately kept off the site. `--unpublish <id>…` takes units off the site |
| `npm run superadmin -- <email>` | Makes an account a platform admin (`--revoke`, `--emulator`) |
| `npm --prefix functions run build` / `test` | Builds or tests the Cloud Functions |
| `npm run cap:android` / `cap:ios` | Creates and opens the native projects |

## App architecture

### Provider tree

```
AuthProvider            Firebase user + custom claims {role, orgId}; claims are read before the user is published
└─ StoreProvider        local state, keyed by uid (or "guest"); switching accounts remounts everything below
   └─ I18nProvider      language from the store
      └─ SettingsProvider   tracks and languages platform admins set up (built-ins first, then content/settings.json);
         │                 fetches the picked language's strings (App waits for them)
         └─ BrowserRouter
            └─ Routed   routes, guards, useCloudSync(uid)
```

- **Firebase loads only when needed.** At startup, `storedSession()` (`fb.ts`) reads Firebase Auth's own persisted session from IndexedDB (or localStorage) without the SDK:
  - **A session is stored:** AuthProvider loads the SDK at once and subscribes to auth state.
  - **None is stored (a guest or new visitor):** nothing loads.
  - **The account screens** call `ensureFirebase()` when they open: the form shows immediately and the SDK arrives while people type. The Google button waits for it, because browsers only allow the sign-in popup straight from a tap. Where the popup can't open (blocked, `operation-not-supported-in-this-environment`) it goes to Google's page with `signInWithRedirect` and comes back to the same address, `?code=` and `?org=1` included; the auth domain is the site's own, so that stays first-party. In-app browsers (Facebook, Instagram, WhatsApp, Telegram, Android WebViews; `inAppBrowser` in `auth/AuthScreens.tsx`), which Google refuses, get "open this page in your phone's browser" with the link to copy instead.
  - **After a sign-in the account screens never navigate.** AuthProvider publishes the account (claims first), the store and router remount at the same address, and `SignedIn` (App.tsx) sends each role on. A `nav()` from the screen ran before that and landed admins in the learner's onboarding (fixed 2026-11-06; `tests/app-routes.test.tsx`).
  - **The SDK can't load** (offline, and its chunk isn't cached yet): AuthProvider sets `offlineUid` from the stored session. That person keeps learning in their own local store and reconnects on the next `online` event.
  - **The rule for new code:** never import `firebase/*` or `./firebase` statically on the guest path. Go through `loadFirebase()`, or keep the module in a lazy chunk. The e2e test "guests never download the Firebase SDK" guards this.
- **One local store per person on the device.** The keys are `darsi:state:<uid>` for accounts and `darsi:state` for guests.
  - An account used on this device for the first time starts from the guest's settings.
  - An account takes over the guest's learning only at the sign-in that created it on this device (sign-up or Google: creation and first sign-in within seconds, less than 10 minutes ago), so "your progress stays on this device until you create an account" holds true. Accounts an organization made never do (they carry an `orgId` claim from the start, and their first sign-in comes later): on a shared phone or lab PC the previous guest's lessons, notes and name must not land in a pupil's school record (`adoptsGuest` in `state/store.tsx`).
  - **Signing out** (`AuthProvider.signOut`, every Sign out button) leaves nothing of the person for the next one: after `pushSignOut` it waits up to 5 s for unsent writes (`waitForPendingWrites`), signs out, terminates Firestore and deletes its cache (`clearIndexedDbPersistence`: an admin's member lists and invite codes, notes), forgets cached org files, and reloads the page as a guest. When everything was sent, the account's local copy keeps its settings, onboarding answers and certificates and forgets progress, notes, weeks, name and organization (`forgetAccount`); sync, the profile and `useOrgBrand` bring them back at the next sign-in. Offline, it keeps them so sync can send them at the next sign-in here, and says so after the reload. A cache delete that didn't finish (`darsi:purgeFs`) is finished when an account screen next opens on a signed-out device, before anything reads Firestore.
- **Guests:** anyone who chose "Continue without an account", or who used Darsi before accounts existed. Guests get the whole learning experience; only cloud features need an account.

Roles are `learner` (independent), `student`, `teacher`, `orgAdmin` and `superadmin`. They live in **Auth custom claims** {role, orgId, and with Darsi Super plan and planUntil}, which only Cloud Functions set, and are mirrored to `users/{uid}` for the UI. When `users/{uid}` changes role or organization, AuthProvider refreshes the token so the security rules see the new claims.

After sign-in, `homeFor(role)` sends org admins to `/admin` and platform admins to `/super`; everyone else goes to `/learn`, and an invite code (`?code=`, carried by "I already have an account" too) to `/org`, which joins with it. Staff routes skip the onboarding gate, and so do platform admins on the learner screens (every course in every track, in the language they use). Teachers and org admins going through onboarding have a link on each step to their own page ("See my students", "Manage your organization"), since there is no navigation until it is done. Signed in, onboarding is the account's: its answers live on `users/{uid}` (see [Cloud sync](#cloud-sync)), so a new device waits a moment for the profile (`profileReady` from AuthProvider) and skips onboarding if the account has done it. Onboarding shows in place of the learning page that was asked for and never navigates when it is done, so that page (a lesson link, a project to review) then opens at its address. Accounts created by an admin with `mustChangePassword` see the set-password screen before anything else; it refuses the password the organization gave out (signing in again with the typed one succeeds only if it is the same), since `passwordChanged` can't compare passwords. A self-registered profile that a function created first (joining from an invite link on a slow connection, through `setRole`) still gets the typed name and language: `createLearnerProfile` falls back to an edit of the person's own profile, and the Google button treats a profile without an email as new.

The window title names the page (`PageTitle` in App.tsx, from the nav item: "Labs — Darsi", «المختبرات — درسي», the organization's name for its members); a screen may set a closer one in its own effect. `index.html` carries the description and the link-preview tags (Open Graph and `twitter:card`, with the 512 px app icon) that WhatsApp and invite links show, and `public/robots.txt` lets search engines index the public pages but not `/super`, `/admin`, `/teach`, `/org`, `/results`, `/__/` or `/api/`. Moving to another page in the app puts focus on its `h1` (Layout; never on the first load), each onboarding step and placement question takes focus from the button that went with the last one, and the tour gives focus back when it ends.

### Layout

At 900 px and wider, a nav rail shows the five learner tabs plus the role's staff links. On phones, the design system's bottom nav keeps five tabs (Learn, Downloads, Labs, Kit, Me), and the staff links live in Me's account section. Students have no Kit tab: the classroom kits are for teaching. Staff screens and the landing page are **lazy chunks** (`React.lazy`), so a learner's phone never downloads or parses them.

## Offline and caching

The service worker (Workbox `generateSW`) installs when a person enters the app. Visitors who only read the landing page never download the offline bundle.

| What | Strategy |
|---|---|
| App shell, learner screens, the light-lesson player, the labs kit, icons, `placement.json`, `labs-manifest.json` and `offline-manifest.json` | **Precached**: 42 files, about 1.3 MB (418 KB gzipped; measured 2026-11-07, see [Performance budget](#performance-budget)). Workbox's list names 50 entries: the app icons and favicon (`includeAssets`) and the web manifest (the plugin's own) are listed a second time by `globPatterns`, with the same revision, so each is stored once |
| Fonts | **Not precached.** Every face has a `unicode-range` (`tokens.json` `type.subsets`), so a page downloads only the scripts it shows. `darsi-fonts` keeps them: cache-first, `ignoreVary`, and only `font/woff2` responses, because Hosting answers a missing path with `index.html`. `platform/fonts.ts` fills it with the page language's faces after load, on every language change and on reconnect: Latin (~76 KB) for English, plus Arabic (~131 KB) for Arabic. Arabic words on a page in another language, such as the language picker or the Arabic brand name, use the phone's own font (`.dr-lang-native`, `.dr-other-script`), so English pages never download Arabic fonts |
| The Firebase SDK (`firebase-*`, including `firebase-extra`: Functions, Storage, Messaging), staff chunks, first-visit screens (landing page, `/upgrade`, the tutor, Report a problem, the tour, `/licences`), exceljs, and their CSS | **Not precached**; `darsi-chunks` caches them cache-first on first use (hashed file names). These are left out by name (`LAZY_SCREENS` and `ON_DEMAND` in `vite.config.ts`); shared chunks the bundler names after one of their modules (`strings`, `data`…) are found at build time instead (`staffOnly`: every module under `src/admin`, `results`, `cms` or `org`, and not loaded at startup) and dropped in `manifestTransforms` |
| Lab apps (`lab-<id>-[hash].js`: 109 apps in 111 chunks, with the shared `lab-agents` and `lab-tiny`; about 1.1 MB, 481 KB gzipped) | **Not precached**; `darsi-labs` caches each cache-first when it is first opened. "Save all labs" on the Labs screen (its size comes from `labs-manifest.json`, written at build time: every lab's on-demand files, shared ones once, gzipped, so what goes over the wire) and a downloaded course pin theirs in `darsi-saved` instead (below). The labs kit (shared chunks such as `LabShell`, `Plot`, `controls`) and its stylesheet are small and precached. See [Labs](#labs) |
| What downloads and "Save all labs" need beyond the precache: the code steps (`CodeSteps`, `sandbox`), a course's labs, its light lessons' packs | **Pinned** in `darsi-saved` (`platform/offline.ts`), by group (`code`, `lab:<id>`, `pack:<id>`, `labs` for every lab; the list is `/__darsi/pins.json` in that cache). `offline-manifest.json` (precached, written at build time) lists each group's files. The `darsi-labs` and `darsi-chunks` routes answer from `darsi-saved` when they have no copy or only an expired one, and nothing ages it out. Chunk names change with every build, so `public/offline-sw.js` (imported into `sw.js` like `push-sw.js`) fetches the new version's files for the pinned groups at install, before the update can take over; without a connection the install fails and is retried later, so a phone that goes offline right after an update keeps working. Any other failure (a full phone) never holds the update back: it goes ahead with what fitted, and Downloads offers "Download again". At activate it removes the previous version's files, unless it couldn't read the new list (a Wi-Fi sign-in page answering), and neither side ever stores a web page as a chunk. Phones on the Chrome 61 build keep every legacy file they have used the same way (`offline-legacy.json`). Downloads checks the pins once per version (`useOfflineRefresh`), and Remove unpins what no other download needs. A code exercise that still can't load offers Retry and "Skip this exercise" |
| `push-sw.js` (push handlers, ~3 KB) and `offline-sw.js` | **Imported** into `sw.js` with `importScripts`, so the browser stores them with the worker; not precached. Their URLs carry a content hash (`?v=…`), so changing one changes `sw.js` and triggers the normal update prompt |
| `/content/placement.json` | **Precached** (312 KB, 72 KB gzipped: the largest file after the entry chunk), so it changes only with a new version of the app. The `/content/` stale-while-revalidate rule (`darsi-content`) is still registered, but the precache answers first and no other shipped file is under `/content/` |
| `/kits/*` | Cache-first (`darsi-kits`). No longer shipped: only phones that downloaded the old built-in kits still have entries, which "Remove" clears |
| `/media/*` | Cache-first with range requests (`darsi-media`), stored only by a download (as uploaded media below) |
| `/lib/*` (Lesson Studio's shared library for light lessons: the cast, extra icons, the mark; ~56 KB before compression) | **Not precached**; cache-first in `darsi-lib` when a light lesson first plays or a unit with one is downloaded. Versioned (`/lib/v1/`), immutable on Hosting, and "Remove" leaves it for the other units |
| `/lib/python/v1/`, `/lib/sql/v1/` and Darsi Tiny (`/lib/tinylm/app/{en,ar}/v2/`, `/lib/tinylm/scene/{en,ar}/v2/`; `/lib/tinylm/v1/` fallback) | **Not precached**; cache-first in `darsi-lib` on first use. A phone fetches only the job and language it opens (~2.8 MB compressed weights, once). Versioned and immutable; none of the four models is in the install bundle |
| Courses (Cloud Storage `…/catalog.json`, `…/units/{id}/v{n}.json`) | Kept by `content/load.ts` itself in `darsi-content`, not by a service-worker rule: catalogs network-first, with the last copy when the network fails or takes over 2.5 s (`SLOW_MS`; the network's copy is stored when it arrives); unit files cache-first (a version's path never changes). A course republished while the phone was away opens offline from the newest version saved. Storing a new version deletes the older ones, except the version a download kept (`setKeptVersions`, registered by `useOfflineRefresh`). See [Authored content](#authored-content) |
| Uploaded media (Cloud Storage videos, captions, kit files, light-lesson audio) | Cache-first with range requests (`darsi-media`) once a unit is downloaded; matched by the Storage path (`/v0/b/<bucket>/o/…`) on any host, so the emulator on the local stack behaves as live. Only the download stores them (`cacheUrls`, which skips files it already has) and only Remove deletes them (every version and language under the course's media folder): the worker's route has no entry cap and never writes, so a fourth download can't push out the first one's files, and streaming or opening a kit without a download stores nothing. A light lesson's JSON (manifest, scenes, timing) is kept by `loadStoredJSON` in `darsi-content`, cache-first |
| Firestore data | The SDK's persistent IndexedDB cache, capped at **10 MB** (the default is 40 MB) |

- **Updates** use prompt mode: a "Reload" toast appears on app screens, never in the middle of a lesson.
- **Downloads** (`screens/Downloads.tsx`) record each course's catalog version and language (`AppState.downloads`). A course whose version or language differs offers "Update", one with files missing "Download again" (checked against Cache Storage when the screen opens); either fetches only what is missing, and an update then deletes the files only the old download used. A saved course with a Darsi Tiny lab (`LAB_MODEL` in `labs/loader.tsx`) offers "Save Darsi Tiny (2.8 MB)" under its row while the model isn't on the phone (its size, read from the model's manifest, is not in the course's); it goes to `darsi-lib`, once for every course, and Remove leaves it. - **The report sheet** ("Report a problem") is a `<dialog>` opened with `showModal()`, so the page behind it is inert; closing it returns the focus to whatever opened it.
- **`/__/` is Hosting's own** (`navigateFallbackDenylist`). - **Hosting headers:** `sw.js` and `index.html` are `no-cache`; hashed assets are cached for a year.
- **The MP4 player** (design system `VideoPlayer`): custom controls drawn on the picture, in the shape people know from YouTube and in Darsi's colours. A thin progress bar thickens on hover and shows the buffered range, chapter ticks, question marks and a time preview. Under it: play, a volume slider that slides out, and the clock; on the other side, captions, a settings menu (playback speed and the caption language, taken from the VTT tracks) and full screen. Opening the transcript to read instead of streaming does the same, for the MP4 and the light lesson. A missing video never blocks a lesson.

## Cloud sync

`src/state/sync.ts` (`useCloudSync`) keeps a signed-in person's progress, notes and certificates in Firestore, where teachers and admins read them.

- **Reads:** progress, notes and `certs` are read once per sign-in, and once more on the `online` event if a read only reached the offline cache. There are no listeners and no polling. The certificates' read stands on its own: if it fails or the rules refuse it, lessons and notes sync as before, and it isn't tried again until the next sign-in.
- **Merge** (`mergeRemote` in `store.tsx`): the newer copy wins. Lessons compare `completedAt`; notes compare their local edit time with `updatedAt`. A lesson first seen from the cloud counts toward the teaching week it was completed in, which keeps streaks correct. Certificates are a union; where both sides have one, the earlier `at` wins, so its date and code stay the first ones.
- **Writes** (`toPush`): only entries the cloud lacks or has an older copy of. Until a read has reached the server, only work finished in this session is written, so a stale phone can never overwrite newer work from another device. Firestore's offline queue carries writes made without a signal. A certificate is created once, only when the cloud lacks it (never rewritten: the rules refuse a second write), and before the certificates' read has reached the server only one earned this session goes. `certDoc` shapes it as the rules want (a course id of 2–64 lowercase letters, digits and dashes; `title`, `track` and `at` only, each within the rules' sizes, counted in UTF-8 bytes; a language that doesn't fit is left out, English first) and holds back one they would never take. Each goes at most once a session: a refused write is never retried in a loop, and it never holds up a lesson or a note.
- **The learning profile** (`learningSync` / `useLearningSync`, `LEARN_KEYS` in `store.tsx`): onboarding's answers and what Me and My tracks change later (`onboarded`, `tracks`, `levels`, `audience`, `stage`, `weeklyLessons`, `teach`) are kept on `users/{uid}` too, so a new device skips onboarding. It reads nothing itself: it works from the profile AuthProvider already reads at sign-in. A device that isn't onboarded takes all of the account's answers at once (or, if the account has none yet, only tracks someone chose there and where they teach, which onboarding starts from). After that the newer copy wins, by `learnAt` (ms; the reducer dates every change to those fields, and a pull keeps the account's date), and the same date with other values on the profile (an admin's edit) is taken. Only the fields that differ are written, each whole (`updateDoc`, so a level or track removed goes too), and the echo of a write ends it. The language and the current track stay per device. Guests are unaffected.
- **Uploads:** project photos are scaled to at most 1280 px and re-encoded as JPEG on the phone before upload (`ProjectView.shrinkImage`). PDFs and anything the browser can't decode go up unchanged. A file still over 10 MB (Storage's limit) is caught before anything goes up, and a retry after a dropped connection sends the files already up instead of uploading them again. The answers stop where the rules do (20,000 characters, 5,000 for how AI was used), and a send the rules refuse says so rather than blaming the connection.
- **Certificates** (`content/cert.ts`, `state.certs`): recorded on the phone the first time they are earned (by Home when a course's last lesson is done, or by Me), so a replay never moves their date or code, and a course republished with another lesson, or unpublished, keeps them. Finding new ones downloads nothing: only courses whose lessons the results (by `unitId`) say are all finished are opened. A capstone's certificate needs every milestone sent (the learner's own `users/{uid}/submissions`, read once; "I'll do it in class and submit later" sends nothing), so guests never get one, and Home moves nobody up for an unfinished capstone. The name on a certificate is the account's (`users/{uid}.name`, as on /super/certificates): Me saves what is typed there and takes a name changed elsewhere. Signed in, each record is also kept in `users/{uid}/certs/{unitId}` (see Writes above), so a new phone gets it back at the next sign-in, even after its course is unpublished; a guest's certificates stay on the phone (an account created from a guest takes them over and sends them). "Reset progress on this device" clears them here only: the next sign-in brings them back. A person's page (PersonDetail) reads that collection once when it opens: a course no longer offered shows the title from the certificate, and a course with a certificate shows as done. /super/certificates still works from the summaries and the catalog, so a certificate of an unpublished course isn't listed there.
- **Certificate codes** (`certCode` in `content/cert.ts`): `DRS-<COURSE>-XXXX-XXXX`, 8 Crockford base-32 characters from a hash of the course, the moment it was earned and the account's uid (none for a guest), so a rename or a replay never moves it and it can't be worked out from what a certificate shows. The code is set when the certificate is recorded (`earnCert`, which knows the store's account) and kept with it, locally and in `users/{uid}/certs` (`code`, optional for records from before). Certificates recorded before 2026-11 had their code worked out from the learner's name each time; a store saved before then freezes the code each one showed at its first load (`withCodes`, `legacyCertCode`). /super/certificates shows `certCode` for the learner's uid, which matches every certificate earned signed in since.
- **Project reviews** (`state/myWork.ts`): Me's "My projects" reads the learner's 20 newest submissions once when it opens, and a project step reads that lesson's (`lessonId ==`, so no composite index), to show each project's status and the reviewer's feedback. No listener. "Send a new version" opens the lesson at that step (`?step=`), which a learner may do in a lesson they have finished; nothing is recorded again. In a lesson they haven't finished, the link opens that project alone (`explore.only`: no step list or Skip, the bar's button is Back, nothing is saved or recorded), and only a project step: a link to any other step starts the lesson as usual. After sending, the notice says who reviews it: their teacher or admins in an organization, else the Darsi team (platform admins on /super/projects).

## Push notifications

Opt-in web push through Firebase Cloud Messaging (FCM). The tone follows the brand rule "Encourage, never punish": no guilt, no threats about losing a streak, no emoji. Setup, browser support and how to send an announcement are in [docs/FIREBASE.md](docs/FIREBASE.md#6-push-notifications).

### Turning it on, per device

The panel in Me (`src/notify/NotificationsPanel.tsx`) is shown to signed-in people only. Guests never touch messaging.

1. **`pushSupport()`** (`src/notify/push.ts`) picks what the panel shows:
   - `unconfigured`: the build has no `VITE_FIREBASE_VAPID_KEY`;
   - `unsupported`: no service worker, `PushManager` or `Notification`;
   - `ios-install`: an iPhone or iPad in a Safari tab (web push needs Add to Home Screen, iOS 16.4+);
   - a permission the person denied: how to allow it in the browser's site settings.
2. **`enablePush(prefs)`:**
   1. `Notification.requestPermission()`;
   2. `getToken()` with the VAPID key and the app's own Workbox service worker registration (there is no `firebase-messaging-sw.js`);
   3. the `registerDevice` callable, with the language, the IANA time zone, the reminder hour, the categories and the weekly goal;
   4. `darsi:push` in localStorage remembers `{ token, on: true, uid }` (the uid keeps a shared phone from refreshing one account's token into another's).
3. **`registerDevice`** stores `users/{uid}/devices/{id}` (`id` = the first 40 hex characters of sha256(token)), sets `users/{uid}.notify`, and subscribes the token to its FCM topics while Announcements are on: `all`, `lang-<code>` (the phone's language: `en`, `ar`, or one platform admins added), `role-<role>`, and `org-<orgId>` in an organization.
4. **On each app start**, `usePushRefresh()` calls `registerDevice` again if `darsi:push.on` and permission is still granted. Tokens can rotate, and this also refreshes `lastSeen`. Changing a preference calls `updateNotifyPrefs`; turning it off calls `unregisterDevice` and deletes the token. Signing out (any Sign out button: `AuthProvider.signOut`) does the same first, so on a shared phone the next person never sees the previous account's notifications; `registerDevice` also moves a token to whoever registers it last (`pushTokens/{deviceId}` records the owner).
5. **Topics follow the person.** When their role, organization or language changes, `onUserTopicsChanged` re-subscribes all their devices.

### What is sent

Each category can be switched off in Me (`notify.cats`).

| Category | Trigger | Who gets it |
|---|---|---|
| Learning reminders (`reminders`) | `dailyNudges`, at the top of every UTC hour (`0 * * * *`): people whose reminder hour (`notify.hourUtc`) is now. `pickNudge` (`functions/src/nudge.ts`) sends at most one a day (see below) | the person |
| Project feedback (`reviews`) | `onSubmissionUpdated`: a submission goes from `submitted` to `approved` or `revise` (opens `/me#projects`). `reviewOrg`: an organization request approved (`orgApproved`, opens `/admin`) or rejected with the reviewer's note (`orgRejected`, opens `/org`) | the person who submitted it, or who asked for the organization |
| Staff alerts (`staff`) | `onSubmissionCreated`: a project is submitted. `requestOrg`: a new organization request | the assigned teacher while they still teach in the student's organization, or else the org admins; platform admins for requests and for capstone milestones queued for Darsi staff (`queue: "staff"`, opens `/super/projects`) |
| Announcements (`news`) | `sendBroadcast` from `/super` | everyone, one organization or one role, through topics |

**`pickNudge(input, now)`** is pure and unit-tested. "Today" is the person's local day in their time zone. The rules apply in order:
1. Nothing if a reminder was already sent today, or if they finished a lesson today.
2. After 7 days without a lesson: one "we saved your place" message. After 21 days: one last message, then silence until they come back.
3. On Saturday or Sunday (UTC), with lessons left for the weekly goal: how many are left.
4. With a streak of 2+ weeks (the app's `streakWeeks` rule) and this week's goal not met yet: the streak.
5. Otherwise, one of three daily messages, rotating by day.

`dailyNudges` also fixes daylight-saving drift: if the person's local hour no longer matches, it rewrites `hourUtc` and waits for the right hour.

### The message and the service worker

- **Payload:** data-only web push with `TTL: 86400` (an offline phone gets it within a day) and `Urgency: normal`. The data is `{ title, body, link, tag, lang, dir }`: in Arabic for Arabic phones, in English for every other language (`wordingFor`); there is no wording in the languages platform admins add.
  - The wording lives in `functions/src/messages.ts`. Names are wrapped in Unicode isolates, and numbers use the language's numerals.
  - Announcements are written in English and Arabic and go out once each: the Arabic text to `'lang-ar' in topics`, the English text to `'all' in topics && !('lang-ar' in topics)` (English phones and every added language), each with the audience's topic added (`&& 'org-<id>' in topics`).
  - Personal messages use `sendEachForMulticast` on the person's devices, grouped by language. Tokens that FCM reports as unregistered or invalid are deleted on the spot.
- **`public/push-sw.js`:** plain JavaScript with no imports and no SDK, loaded into Workbox's `sw.js` (`workbox.importScripts` in `vite.config.ts`).
  - `push`: reads `payload.data` and calls `showNotification` with the Darsi icon, the monochrome badge, `lang` and `dir`.
  - Tags: a new reminder replaces the previous one (`darsi-nudge`); reviews, staff alerts and announcements each have their own tag.
  - `notificationclick`: focuses an open Darsi window and navigates it to the link, or opens a new window. Only paths inside the app are followed; anything else opens `/learn`.
- **Data and battery:** the messaging SDK sits in the lazy `firebase-extra` chunk, so signing in alone never downloads it. It loads when someone turns notifications on, or when the app refreshes an enabled token at start. A push is a few hundred bytes. There are no listeners and no polling.

### Security rules

**Firestore** (`firebase/firestore.rules`):
- **`users/{uid}`:**
  - *Read:* the person, a platform admin, their organization's admins, and their assigned teacher.
  - *Self-registration:* only as an independent `learner`, with a fixed list of fields, each typed and bounded, `email` equal to the token's email in lower case (nobody can claim another person's address), `createdAt` the request's own time, and never for a `@users.darsi.app` login (those are for accounts organizations make).
  - *Self-edits:* never email, role, organization, teacher, summary, `notify` or `mustChangePassword` (only `passwordChanged` clears it). The fields a write changes are type- and size-checked, elements included (`profileOk`: at most 30 tracks joining to 750 characters, levels 0–12; the learning profile's `onboarded` a boolean, `audience` teachers or students, `stage` one of the four, `learnAt` an integer of ms).
  - *Org admins:* may change only group, teacher, active flag and name, typed (`memberOk`).
- **`progress`:** written only by its owner, under its own `lessonId` (`[a-z0-9][a-z0-9-]{1,99}`). Only the listed keys, each typed and bounded: `accuracy` 0–1, `xp` an integer 0–100, `seconds` an integer up to 86,400,000, `completedAt` a string, `unitId` ≤ 64, `track` ≤ 24, `competencies` ≤ 30 strings joining to 1,230 characters. Nobody can delete it. The summary counts only published lessons, with the unit's own course, track and competencies (`onProgressWrite`).
- **`submissions`:** created by the owner with status `submitted`, `createdAt == request.time`, the token's own `orgId`, and only the fields `ProjectView` writes, typed and bounded. `fileUrl` and each `files[].url` must be a download link of this project's Storage (or the local emulator) under `submissions/<org>/<their uid>/`. No reviewer field can be set at creation, nor a capstone's `checks`, `aiReview` or `queue`: `checkCapstone` writes capstone milestones with the Admin SDK. Reviewed by the person's assigned teacher, the admins of the organization the person is in now (not the one the work was sent from) or a platform admin, who can change only status (submitted, approved or revise), score, feedback (≤ 5,000) and reviewer fields, as themselves.
- **`notes`:** the owner only; `{text ≤ 50,000, updatedAt}`.
- **`certs`:** created once by the owner (`title` per language, `track`, `at`, each bounded, and optionally its `code`: `DRS-` and up to 86 capitals, digits and dashes); read like the person's lessons; nobody changes or deletes one.
- **`courseAccess/{uid}`:** written and deleted by platform admins only (`units` ≤ 50, `grantedBy` themselves); read by its owner and platform admins. A granted university teacher reads `progress` and `submissions` of those courses across all learners (collection-group rules on `unitId`) and writes none of them.
- **`users/{uid}/private/…`, `paymobOrders`, `tutorLeases`:** no client access (functions only).
- **`devices`** (push tokens) and **`pushTokens`** (their owners): no client access at all, not even the owner's.
- **`orgs`:** readable by members, the requester and platform admins, so the document holds nothing private. Never created from a client (`requestOrg`, `createOrg`). Its admins change only `name` and `brand` (below); country and city are a platform admin's (`updateOrg`). Nobody writes `courses` from a client, platform admins included: only `setOrgCourses`, which checks its shape and size, since every member's phone reads it. The same holds for `site` (its own web address): only `setOrgSite`, which keeps one organization per host in `config/sites`. `orgs/{orgId}/private/…` (the invite codes, the request's contact and reason) is read by its admins and platform admins and written only by the functions.
- **`broadcasts`:** readable by platform admins; written only by `sendBroadcast`.
- **`inviteCodes`:** no client access at all.
- **`units` and `unitDrafts`** (course editor): `canEdit(owner)` is a platform admin, or that organization's admin for an org `owner`.
  - *Create:* `idFits`: org units need a generated id (`u` + 8 characters, `[a-z0-9]`), so they can never shadow a built-in or public unit; `rev` starts at 1 and `published` must be null. A draft is created only beside a `units` doc of the same owner (the editor writes both in one batch), and a unit can't be created over another owner's draft. `publishDraft` also checks the draft's owner.
  - *Update:* `nextRev`: every save sets `rev` to exactly the stored `rev + 1`, so a second editor with a stale copy is refused instead of silently overwriting; `owner` and `published` can't change.
  - *Delete:* only while unpublished; `deleteUnit` handles published units.
  - Students and teachers never read drafts; learners get published units from Storage.
- **`config/{doc}`** (platform settings): platform admins read; nobody writes from a client (`saveSettings` and `publishLanguage` do). Everyone else reads the published copy, `content/settings.json`.
- **`translations/{code}`** (languages being added): platform admins only. The id must equal `code`, every save sets `rev` to exactly `rev + 1`, `published` is never written from a client, and a draft can be deleted only while unpublished.
- **`orgs/{orgId}` branding:** its admins may change `name` (2–80 characters) and `brand`: only `logo` and `v`, and `logo` must be null or a file `orgs/{orgId}/brand/logo-<6–32 of [a-z0-9]>.(png|webp|jpg)` of that same org.
- **`stats`, `analytics`, `analyticsDevices`:** platform admins read; nobody writes from a client (the functions do).
- **`config/analytics`:** platform admins read and write it; `measurementId` must be empty or `G-…`, and only the listed keys are accepted.

**Storage** (`firebase/storage.rules` on `darsi-f0685`):
- `media/` and `kits/` are publicly readable and never writable from the client.
- `submissions/{orgId|none}/{uid}/{unitId}/{file}` (and the older `submissions/{orgId|none}/{uid}/{file}`) is created only by its owner, in their own organization's folder (`none` without one): under 10 MB; JPEG, PNG, WebP, GIF or HEIC photos, PDF, MP4 or common audio (never SVG or HTML); named as `ProjectView` names files (`{lessonId}-{ms}-{name}`). It can be read by the owner, a platform admin, that organization's admins, the student's own teacher, and university teachers granted the course. (Download links carry their own token, so these read rules cover SDK reads only.)
- `content/**` (public authored units) is readable by anyone, guests included. `orgs/{orgId}/**` is readable only by that organization's members and platform admins.
- Media uploads go to `content/media/{unitId}/` (platform admins) and `orgs/{orgId}/media/{unitId}/` (that org's admins, platform admins): MP4 ≤ 60 MB, VTT ≤ 512 KB, PDF or PPTX ≤ 20 MB. No client ever writes the unit JSON or `catalog.json`; the functions do.
- The org's logo goes to `orgs/{orgId}/brand/logo-<id>.(png|webp|jpg)` (its admins, platform admins): PNG, WebP or JPEG, ≤ 100 KB. Its members read it like the rest of `orgs/{orgId}/`.

## Organization branding

An organization chooses its name and logo, and its members see them where the app shows Darsi's brand: the app bar on every screen, the nav rail (with a small "with Darsi" credit), certificates (the org's logo first, Darsi's mark beside it, the org as issuer), Me's account section and the browser tab's title.

- **Editing:** `admin/OrgBranding.tsx`, on the org dashboard (/admin) and on a platform admin's org page (/super/orgs/:id). The picker takes PNG, JPEG or WebP (not SVG, which `createImageBitmap` can't decode). The logo is shrunk on the admin's device to at most 256 px, WebP where the browser can write it (PNG otherwise, transparency kept) and under 100 KB, then uploaded to `orgs/{orgId}/brand/logo-<random>.<ext>` with a one-year cache. Saving writes `name` and `brand {logo, v + 1}` and deletes the previous file.
- **On members' phones:** `state/orgBrand.ts` (`useOrgBrand`, called by App) reads `orgs/{orgId}` once per sign-in, with no listener. The logo is fetched only when `brand.v` changed, and kept in the person's local store as a data: URL (`state.org`), so it shows offline and costs nothing after the first download. Leaving the org (or signing out) brings Darsi's look back.
- **In the design system:** `BrandProvider` (App sets it from `state.org`), `useBrand` and `BrandMark` (the org's logo, or Darsi's mark). `AppBar` and `CertificateCard` use them, so screens need no changes.
- **Not branded:** the installed app's name and icon (the web manifest is the same for everyone), Darsi's landing page (an organization's own web address has its own: [Organization sites](#organization-sites-custom-web-addresses)), and the classroom kits (PDF/PPTX built ahead of time).

## Organization sites (custom web addresses)

An organization can have its own web address, such as cis.darsiai.org (2026-11-08). Anyone who opens it sees the organization's name and logo, before signing in and after, and platform admins choose whether Darsi's identity shows there ("with Darsi") or not at all. Every address is served by the same Hosting site and the same build as darsiai.org, so the app works out at run time which organization a host belongs to.

- **Setting it** (platform admins): the "Web address" panel on `/super/orgs/:orgId` (`admin/OrgSite.tsx`, in the Analytics chunk): the host (what is pasted is cut to a host: `https://CIS.darsiai.org/x` is `cis.darsiai.org`), a "Show Darsi's identity" switch (on by default), Remove with an inline confirmation, and a fold-out list of what a new address still needs outside the app (below). Saving goes through `setOrgSite`; its refusals (`site-host`, `site-reserved`, `site-taken`) show in the admin's language (`admin/refusals.ts`).
- **The rules for a host** (`content/sites.ts`, shared with the functions): a lowercase hostname of at least two labels whose last has a letter (so no IP address), at most 253 characters, never Darsi's own (`darsiai.org`, `www.darsiai.org`) or Hosting's (`*.web.app`, `*.firebaseapp.com`). `isDarsiHost` also counts `localhost`, `*.localhost` and IP addresses, which the app never looks up.
- **The data:** `orgs/{orgId}.site {host, darsi}`, written only by `setOrgSite` (the rules refuse it from every client), and `config/sites {list [{host, orgId}]}`, which keeps one organization per host in a transaction (a host whose organization no longer exists can be taken over).
- **The public file** `content/sites.json` (public, `max-age=60`, gzipped like the other JSON files): `{ v (when it was published, ms), sites: { "<host>": { orgId, name, logo (a public https URL, or null), darsi } } }`. An organization's own logo (`orgs/{orgId}/brand/…`) is readable by its members only, so it is copied to `content/sites/{orgId}/{sha256 of its bytes, 20 hex}.{webp|png|jpg|jpeg}` (public, one-year immutable cache) and the file points at the copy (`publicFileUrl`: Firebase Storage's REST address, which answers every origin). Copies nothing lists any more are deleted at each publish. `setOrgSite` publishes the file, and so does `onOrgSite` when an organization with a site is renamed, re-branded or deleted. Storage refuses two changes to one file within about a second (429), so a publish tries again up to four times, waiting 1.2 s and then twice as long each time.
- **On a phone** (`state/site.ts`, startup code, no Firebase): on a host that isn't Darsi's own, the app reads `content/sites.json` once per start with a plain `fetch` (`loadSitesFile` in `content/load.ts`: network-first, the last copy in `darsi-content` answering offline or after 2.5 s). The host's entry is kept in localStorage (`darsi:site:<host>`), the logo as a data: URL (at most 160 KB, PNG, WebP or JPEG), so the next start shows it at once, offline too, while the file is re-read behind it; a change shows as soon as it arrives. Only a first visit waits for the file (the loading screen), for at most 8 s, after which Darsi's look shows until it comes. Darsi's own hosts read nothing. On this machine, `?site=<host>` on localhost stands in for a host until the tab closes (`?site=` stops it), for testing on the local stack; on a real address it is ignored.
- **The brand** (`identityOf`): a member of an organization sees their own, as before (on their organization's site, its published name and logo fill in what their phone doesn't have yet); anyone else on a site sees the site's. Whether Darsi's identity shows is the site's choice, and it always shows on Darsi's own addresses. App passes the brand to the design system's `BrandProvider` (`logo`, `name`, `darsi`), so the app bar, the nav rail ("with Darsi" only when it shows), certificates (Darsi's small mark only when it shows) and `BrandMark` everywhere follow it. Without a logo and without Darsi's identity, `BrandMark` shows the name's first letter instead of Darsi's mark. The window title is "<page> — <organization>", or the organization's name alone where Darsi's was.
- **Where it shows:** the app bar, the nav rail, the window title, the landing page (`SiteLanding` in `landing/Landing.tsx`: the logo, the name, "with Darsi" when it shows, then Sign in, Create an account and Continue without an account, with none of Darsi's marketing sections), the sign-in and sign-up screens (the logo and the name above the title), onboarding's welcome (the logo and the name) and certificates.
- **Without Darsi's identity**, `I18nProvider` gets the organization's name (`brand`), and `t()` puts it, isolated, wherever a UI string says "Darsi" or «درسي» (`rebrand`). It does so before the variables go in, so a name someone typed is never changed. That covers every string of the app and of its lazy chunks (admin, editor, tour, tutor, Super): "A new version of CIS Training Platform is ready". Kept as written: "Darsi Tiny" («درسي الصغير»), a model's name that the labs and courses use too; the "Darsi skills" framework name; the branding panel's hints and the web address panel's strings, which are about Darsi's identity; `/licences`, which keeps naming Darsi's software; and course and lab content, which is authored material (lessons and narrated videos that mention Darsi still do).

## Analytics

Two sources, both read with one-shot reads on `/super/analytics`:

- **Accounts and organizations** (`stats/overview`): `statsJob` (daily) and `refreshStats` (the Refresh button) read every user's role, organization, dates and summary with a `select()`, and every organization. They count accounts, roles, new and active accounts (by `lastActive` or the last lesson), lessons, XP, the average score and lessons per ISO week, and for each active organization its members, teachers, students, activity, lessons and score. Pending and rejected organizations are only counted.
- **Usage from phones** (`analytics/{day}`, `analyticsDevices`), guests included. Every phone queues events and sends them in batches to `collect`.

**On the phone** (`analytics/track.ts`, startup code, no Firebase; `useAnalytics` in App):
- `track()` adds an event to a queue in IndexedDB (`darsi:events`, at most 300) and never waits for the network. Events made offline carry `o: 1`.
- A batch (at most 100 events) goes to `/api/collect` on the same site, gzipped with `CompressionStream` where available (`?z=1`). It is sent when 30 events have built up, when the app goes to the background (at most every 15 minutes), when the connection returns, and at once when someone signs in or out, so events go out as the account that made them. With Data saver or the browser's Save-Data, it waits for 100 events or a day. No timers, no polling. A failed send keeps the batch; one refused as malformed (400/413) is dropped.
- Events: `session_start`, `screen_view` (the path's first part), `lesson_start`, `lesson_complete` (unit, lesson, track, score, seconds, XP), `lab_open`, `unit_download` (unit, MB), `onboarding_done`, `sign_up` and `sign_in` (method). None from the course editor's preview.
- A batch says who sent it: a random id made on the phone (`darsi:device`), the role (`guest` without an account), audience, language, organization id and whether the app is installed. Never a name, email or answer. Me has a switch to stop it ("Share anonymous usage statistics"); switched off, the queue is emptied.
- Cost: about 2 KB of startup JavaScript (gzipped). A batch of 30 events is about 1 KB gzipped, usually one request per session.

**On the server** (`functions/src/analytics.ts`; the pure parts, tested, in `analyticsCore.ts`):
- `parseBatch` keeps only known events and parameters (ids, short words, numbers clamped to a range) from the last 30 days, and never more than 10 minutes ahead.
- `sanitize` then keeps a phone's ids only where Darsi knows them: published courses (public, and the org's own for its members), Labs apps (`functions/src/shared/labs.ts`, generated from the app's lab folders by `copy-shared.mjs`), active organizations, tracks, published languages and a fixed list of screens. Anything else counts as `other`, so the day's document can't be filled with made-up keys.
- `dailyCounts` adds them to `analytics/{yyyy-mm-dd}` with increments, so batches arriving together add up.
- A phone's first batch of the day adds to `dev` (and `devNew` the first time ever). `analyticsDevices/{id}.last` gives active phones for 1, 7 and 30 days through count queries.
- Organization figures from phones are what the phone says, so the dashboard takes members, activity and scores from `stats/overview` and uses the phones' counts only for the org's lessons-per-day chart.
- **Google Analytics** (Firebase's web stream): once a platform admin sets the measurement ID and a Measurement Protocol API secret on /super/analytics (`config/analytics`), `collect` forwards each batch: 25 events per request, the last 72 hours only, the phone's random id as `client_id`, role, audience, language and installed as user properties, and `engagement_time_msec` so visits count as engaged. Every account type is forwarded, students included (the user's choice), with no personal data. The Firebase Analytics SDK (gtag) is not used: it would cost every phone about 50 KB, load Firebase for guests and lose events made offline.

**The screen** (`admin/Analytics.tsx`, a lazy chunk with its own strings in `admin/strings/` and `styles/analytics.css`):
- Tiles: active phones, accounts, active accounts, lessons, average score, organizations.
- Bars per day for 30 days (active phones, lessons, visits), plus the offline and installed shares and downloads.
- The top tracks, courses, labs, languages, roles and screens.
- The organizations table, people (the 50 most recently active, or a name search), and the Google Analytics connection.
- `/super/orgs/:id` has one organization's figures, its lessons per day, its branding and its people; `/super/people/:uid` is the person page.

## Problem reports

Anyone can report a problem from any screen, guests included: a round button with a bug at the inline start of the screen (above the bottom nav and the lesson's Continue bar), and "Report a problem" at the foot of the nav rail from 900 px, where the floating button hides (`Layout` sets `data-rail` on `<html>`). On the landing page, whose main button sits where it would float, it closes the page after the footer instead.
- **It never covers a control or the answer sheet** (nor does the tutor's button): both stand on `--fab-end` (app.css), which rises above the answer sheet while it shows (LessonPlayer puts the sheet's height in `--sheet-h` on `<html>`). Below 900 px they also step aside (`useFabsAside` in `bugs/Fab.tsx` sets `data-fabs` on `<html>`): "away" while the page scrolls down (back when it scrolls up, reaches its top or end, or another page opens) and while a video's checkpoint question shows; "sheet" while the answer sheet shows, when the Report button goes and the tutor's sits in the sheet's head beside "Correct!", so "why?" stays in reach without covering the chosen answer. Hidden means faded and not tappable, never removed: keyboards and screen readers still reach them, focus shows them, and so does the tour. One passive scroll listener read once per frame, and observers on `<html>`'s style and (lesson screens only) class changes; no polling. Pages leave `--fab-clear` at their foot (the lesson, the app frame on phones, the pages with no bar, the editor's preview) so the last line scrolls clear, the root's `scroll-padding-block-end` keeps focused controls above the band and the bars (WCAG 2.4.11), and the editor's bar leaves its inline start to the button on phones. No `:has()` (old WebViews). `tests/fab-room.test.tsx` guards all of it.

**On the phone:**
- `bugs/log.ts` (startup, imports nothing, ~1 KB with the button): from `main.tsx` on, it keeps the last 25 errors, unhandled rejections, `console.error` calls, failed loads (scripts, pictures) and failed or refused requests (method, path and status; never a query or a body; requests their own code cancelled are skipped), plus the last 15 pages. In memory only; it leaves the phone only inside a report.
- `bugs/Fab.tsx` (startup): the button, and `ReportBug` in App. The first tap loads the `Report` chunk (~14 KB gzipped, with `modern-screenshot` 4.7.0; not precached), which takes a picture of the screen first, without the button (nor index.html's `<noscript>`, whose text would show as raw markup; `inShot`), then opens the sheet over it.
- The picture: the part of the page on screen (`domToCanvas` of `<body>`, shifted by the window's scroll), at most 1600 px on the long side, JPEG at 0.72 (lower if it would pass ~1.1 MB): about 35 KB on a phone and 110 KB on a laptop. Its fonts are the page language's own (`familiesFor`), inlined from the fonts cache, so an English page never fetches the Arabic files. A browser that can't draw it gets the sheet without one, and anyone can add a picture of their own (shrunk on the phone).
- The sheet (`bugs/Report.tsx`, `styles/bug.css`; a bottom sheet on phones, a panel at the inline start from 900 px): "What went wrong?" (at least 3 characters), the picture with a switch to leave it out, a plain list of what else is sent, and "See everything that is sent" with the exact JSON.
- What goes with the words and the picture (`gather`): the page (address with secret-looking query values replaced by "…", title, scroll, language, direction), the app (build file, service worker, installed, storage used), the device (user agent, platform, languages, viewport, screen, pixel ratio, orientation, touch, memory, cores, time zone, local time, reduced motion), the connection (online, type, speed, Data saver), the account as the app knows it, the learner's settings (language, audience, stage, tracks, levels, weekly goal, lessons finished, downloads, Data saver, organization) and the log.
- It goes to `/api/bug` with a plain `fetch` (guests never load Firebase); signed in, with the ID token. Offline, or when the request can't get through, the report waits in IndexedDB (`darsi:reports`, at most 5, dropped after 30 days) and goes at the next start or when the connection returns, with the token only if the same account is still signed in (its details still say whose it was). 429 says to wait a few minutes.

**On the server** (`functions/src/bugs.ts`; the pure parts, tested, in `bugsCore.ts`): `reportBug`, an HTTP function behind the Hosting rewrite `/api/bug` (max 2 instances).
- `parseReport` checks everything: the words (3–4,000 characters), the address (secrets replaced again), the details (`clean`: plain data only, strings ≤ 2,000 characters, ≤ 80 keys and 60 items, 6 levels, ≤ 48 KB), and the picture (a JPEG, PNG or WebP data: URL of ≤ 1.2 MB whose own bytes say it is that image; SVG and anything else is refused). The body is at most 1.7 MB.
- Who sent it comes only from the ID token, verified with revocation checked (a bad token is refused with 401, never stored as a guest), plus the profile's name: uid, email, name, role, organization, plan and sign-in method.
- Limits per instance: 8 reports per address per 10 minutes, 10 per account per hour, 120 per hour in all.
- It writes `bugReports/{id}` {createdAt, status "new", text, url, path, user, shot {path, bytes, type, w, h}, details, server {ua, lang}} and the picture to `bugReports/{id}.{jpg|png|webp}` in the app's bucket.
- Rules: only platform admins read either; they change only `status` ("new", "fixed", "closed"), signed with their own uid and the request time; nobody creates or deletes a report from a client (`tests-rules/security.rules.test.ts`). Index: `bugReports (status, createdAt desc)`.

**For platform admins** (`/super/bugs`, "Problem reports" in the nav; `admin/Bugs.tsx` in the SuperAdmin chunk): the new reports or all of them, newest first, 30 at a time, read once. Each shows the words, who (a link to their person page) or "A guest", the page, the browser and screen at a glance, the connection, the last errors, the picture (downloaded only when opened), all the details, and Mark fixed, Close it, Reopen and "Copy the details" (the whole report as JSON, for a ticket or a coding assistant).

## Darsi Super

The paid tier: a live tutor for the courses (docs/SUPER.md has the plan and phases). Phase 0 (the groundwork), phase 1 (payments) and phase 2 (the tutor) are built. Server code is `functions/src/billing.ts`, `payments.ts`, `tutor.ts` and `relay.ts`, with the pure parts, tested, in `billingCore.ts`, `paymentsCore.ts` and `tutorCore.ts`.

**Who has Super:**
- Their own subscription (`subscriptions/{uid}`: plan, status, source `paymob`/`stripe`/`grant`, `currentPeriodEnd`), paid or cancelled but not yet ended; or a seat in their organization's licence (`orgs/{id}.licence` {plan, seats, until} and `users/{uid}.superSeat`). If both apply, the one that lasts longer counts (`entitlement`).
- It goes into the custom claims beside role and organization: `{role, orgId, plan, planUntil}`. Every claims write goes through `writeClaims(uid, role, orgId)`, so a role change (`setRole`, `setUserRole`, `joinOrg`, deleting an org) keeps Super. `createMembers` still sets claims directly, because a new account has no plan. The profile mirrors it (`plan`, `planUntil`, `planSource`) for the admin screens.
- `onSubscriptionWrite` and `onOrgLicence` (a licence change refreshes every seat holder) rewrite the claims. AuthProvider refreshes the token when the profile's `planUntil` differs from the claim's, and exposes `useAuth().plan`.
- Changing organization clears `superSeat`.

**Plans, credits and the margin:**
- Platform admins edit the plans on /super/plans (`admin/Plans.tsx`; it loads with the SuperAdmin chunk, because a lazy route of its own split the startup bundle). `savePlans` stores `config/plans` {plans, economics} and publishes the active plans, without the costs, as `content/plans.json` for the Upgrade screen.
- **The switch:** /super/plans starts with "Darsi Super for everyone", on or off (`setSuperOn`, platform admins). It is `config/settings.superOn` (missing means on), published as `super` in `content/settings.json`, which every phone already reads once per start; `useSuperOn()` (`content/settings.tsx`) remembers the last value in localStorage so a phone where it is off never flashes the tutor. Off: the tutor's button and the Me card are hidden, and /upgrade shows only "Darsi Super isn't available right now" (App passes `superOn` into Upgrade; the plans aren't read), plus Cancel renewal for a card subscription that still renews; `tutorConfig()` reports `on: false`, so `tutorAsk`, `tutorStatus` and the voice relay refuse with `tutor-closed`; `startCheckout` refuses with `super-off`. Subscriptions, credits and the webhooks are untouched, so payments already under way still complete and turning it on again gives everyone back what they had. The relay reads the switch only after it is redeployed with this code.
- A plan is for one person (monthly or yearly), a seat in an organization (priced per seat), or a pack of extra credits (kind `credits`, for people who already have Super). Each has prices in EGP (Paymob) and USD (Stripe) and a number of tutor credits.
- **Credits** (`credits/{uid}` {plan, planUntil, packs}): each paid period brings the plan's credits, and what was left of the last period lapses at its end. A period paid while the last one still runs (an early Paymob renewal, or a plan on top of a running one) adds its credits to what is left, all of it to the new end (`extendPlanCredits`); a new period of the same Stripe subscription replaces them. Packs never expire. Spending takes the period's credits first (`spendCredits`). A stored figure that isn't a number counts as 0 and heals on the next write, and a cost that isn't a number charges the whole hold (fail closed).
- **Economics** {usdPerCredit, egpPerUsd}: what one credit costs Darsi at the AI provider, and the exchange rate. The tutor will debit each call at its measured cost (`creditsForCost`, rounded up).
- **The user's rule: at least 60% margin** (`MIN_MARGIN`). `validatePlans` refuses any price whose credits, all used, would cost the provider more than 40% of it: margin = 1 − credits × usdPerCredit ÷ price in USD. The page shows each price's margin as you type. The margin counts the AI provider's cost only, not payment fees or hosting.
- Platform admins can give complimentary Super (`grantSuper`, days, never counted as revenue; it brings the plan's credits for those days) and extra credits (`grantCredits`, into packs) on a person's page. Taking Super back (`revoke: true`) ends a running subscription and its period's credits now, in one transaction with `credits/{uid}`, and keeps the packs (`revokeEffects`; a second take-back writes nothing). The person page words the plan (its name from `config/plans`), status and source, and decides "Has Super" from the subscription it just read, since the profile's copy is written by a trigger a moment later.
- `savePlans` refusals carry `details: {reason, …numbers}` (`PlanError`: `plan-margin` with `margin` as a fraction, `plan-id`, `eco-rate` …), so /super/plans says them in the page's language with its numerals; a reason it doesn't know shows the server's English.

**Organizations:** `setOrgLicence` (platform admins: plan, seats 1–100000, days ≥ 1; removing is its own `remove: true`, as taking Super back is `grantSuper`'s `revoke: true`, so an empty field never does either, and both ask first on the page) on the org page. Org admins give and take seats (`setSeat`, refused when all are taken) or fill the free ones (`fillSeats`: teachers first, then students; org admins get one only by hand) on their dashboard, which also links to /upgrade with the licence's seats filled in (`?seats=`).
- **A licence sells seat-time** (`licenceAfterPayment`): an expired or missing licence becomes the seats paid for, for the plan's period; a live one gets the larger seat count and an end that keeps every seat-day it had plus every one paid for. Renewing the same seats adds a year; one seat bought for a 1000-seat licence adds about 9 hours.
- **A licence that shrinks frees seats** (`onOrgLicence`, `seatsToRelease`): holders beyond its seats lose theirs, staff first kept (org admins, teachers), then students, by name; a removed licence takes none (they come back with it). The trigger runs up to 540 s, retried for six hours, and refreshes claims 25 at a time; `writeClaims` skips claims that already match, so a retry is cheap.

**Checkouts** (`payments.ts`):
- `startCheckout` {plan, currency, seats?, clientId?}: EGP goes to Paymob, USD to Stripe. A plan for one person needs an account; a pack needs Super already; seats are bought by an org admin for their organization (the price per seat × seats).
- It stores `checkouts/{id}` {uid, orgId, kind, plan (a copy), currency, amount, cents, seats, provider, clientId, status}, the record every webhook is checked against, and returns the provider's page:
  - **Paymob:** an intention (`/v1/intention/`: amount in piastres, the integration ids, the account's email and "NA" for the other billing fields, `special_reference` = the checkout id, `notification_url` = `paymobWebhook`, `redirection_url` = `/upgrade?done=<id>`), then Unified Checkout with the public key and the client secret. Each payment is one period: Paymob's wallets and kiosks can't renew.
  - **Stripe:** a Checkout Session with inline prices: a subscription that renews itself for a plan for one person, a one-off payment for a pack or a licence. The checkout id rides as `client_reference_id` and in the metadata.
- A provider without keys (missing, or the secret set to `unset`) answers `failed-precondition: payments-closed`, and the Super screen says payments open soon.
- **Keys:** secrets `PAYMOB_SECRET_KEY`, `PAYMOB_HMAC_SECRET`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`; params (`functions/.env`) `PAYMOB_PUBLIC_KEY`, `PAYMOB_INTEGRATIONS`, and optionally `PAYMOB_BASE`, `STRIPE_BASE` and `SITE_URL`. Every functions deploy needs the four secrets to exist (docs/FIREBASE.md §9).

**Webhooks** (`paymobWebhook`, `stripeWebhook`; HTTPS, at most 5 instances):
- **Paymob:** the "transaction processed" callback, checked with HMAC-SHA512 over Paymob's 20 fields (`?hmac=`). A successful, not pending transaction pays the checkout named by `order.merchant_order_id`; its transaction id is the payment's ref. A full refund or a void refunds it; a partial refund is left alone.
- **Stripe:** the signature (`Stripe-Signature`, HMAC-SHA256 of `t.body`, 5 minutes) on the raw body. Sessions and invoices are read back from Stripe in API version 2024-06-20, so their shape doesn't depend on the endpoint's settings. `checkout.session.completed` (and `async_payment_succeeded`) pays the checkout and maps the subscription (`stripeSubs/{id}`, and `stripeSub` on `subscriptions/{uid}`); `invoice.paid` pays the renewals (not the first invoice); each runs to the end of the period its invoice's lines paid for (calendar months) plus 2 days' grace (`STRIPE_GRACE_MS`) for Stripe's hour-late charge and card retries, but never less than that period's length after time already paid (a card subscription started while a Paymob or complimentary period runs is added after it, and its renewals keep that lead); `charge.refunded` (full only) refunds; `customer.subscription.updated` (read back from Stripe) records a renewal cancelled or restored, or a failing card (`past_due`); `customer.subscription.deleted` marks the subscription cancelled, and Super lasts to the end of what was paid. Events of a subscription the person no longer has (their `subscriptions/{uid}` isn't a card one, or holds another `stripeSub`) change nothing. Both webhooks refuse everything while their signing secret is the placeholder `unset` (`realSecret`): that word is public, so it can't count as a signature. The payment intent id is the payment's ref. A failure answers 500 so Stripe retries.
- Every payment must match its checkout's amount and currency, or it is logged and not recorded.

**Payments and revenue** (only the webhooks call these; nothing calls them from a phone):
- `recordPayment` writes `payments/{provider}_{ref}`, what it buys (`paymentEffects`) and its checkout's status in one transaction: all of it or none, so a webhook that failed half-way is retried in full and a repeated one does nothing. A Paymob subscription payment adds a period from the current end (on a card subscription that still runs, that subscription keeps its source, renewal status and `stripeSub`; otherwise a stale `stripeSub` is dropped); a Stripe one runs to its invoice's period end; a pack adds credits; a licence gets seat-time. The payment keeps what it did (`added` {ms, credits}, or `licence` {before, after}) so a refund takes back exactly that: a licence goes back to `before` unless something changed it since (then it loses the seat-time paid). A licence for an organization that is gone is kept as `unapplied` and audited (`paymentUnapplied`) for a platform admin.
- Each payment adds to `analytics/{day}.revenue.{EGP|USD}` {value, n} and the plan count, and is sent to Google Analytics as a GA4 `purchase` through the Measurement Protocol (`revenueEvent`): `transaction_id`, value, currency, affiliation (individual, organization or credits), the item (a licence is priced per seat), `client_id` from the phone when the checkout passes it, and `user_id` as a hash of the account id. `recordRefund` marks the payment, counts it in `refunds` and sends `refund`; access runs to the end of the period.
- `checkRevenueEvent` (the Plans page) sends a sample purchase to Google's validation server, which records nothing.
- `stats/overview.super` counts live subscriptions by plan and source, and licences with their seats and seats used. /super/analytics shows revenue for 30 days per currency and a Super tile.

**Rules:** `subscriptions` and `credits` are readable by their owner and platform admins; `payments` and `checkouts` by platform admins only; `stripeSubs` by nobody. No client writes any of them.

**On the phone:**
- `/upgrade` (`upgrade/Upgrade.tsx`, a lazy chunk with its own strings, not precached, no Firebase) reads `content/plans.json` with a plain `fetch`, so guests see it too. App passes the address in (`plansUrl`): importing `content/load` from the chunk split the startup bundle. It shows EGP for Arabic or Egypt's time zone and USD otherwise (switchable), the per-period credits, licences for organizations (org admins choose seats and buy), and packs only to people who have Super. Buy calls `startCheckout` (passed in by App, like `plansUrl`) with the phone's analytics id, and opens the provider's page. Coming back with `?done=` reads the token again once, 4 seconds later, with "Check again" for a slow webhook.
- Me has a Darsi Super card (status, or "See Darsi Super").
- Funnel events: `view_paywall` {from} and `begin_checkout` {plan, cur, prov}.

**The tutor** (phase 2; `tutor.ts`, `relay.ts`, the pure parts in `tutorCore.ts`):
- **Courses:** it reads the published catalogs (public, plus the learner's organization's) and unit files from Storage, cached for 30 minutes in a small LRU per kind on each instance (a search index is about 1.6 MB, and keeping every one could fill a 512 MiB instance). A lesson becomes sections (video transcript, reading with key terms, practice with explanations, project), each with an id `<lessonId>/<stepId>`.
- **Search:** BM25 over every section of the unit's track. A section whose key terms the question names gets a bonus (`TERM_BONUS`), and the learner's own course counts 1.5× (`OWN_COURSE`); "example", «مثال» and similar words don't count. Arabic is folded (alef forms, ya, ta marbuta, no diacritics, "al-" dropped). It searches the learner's language and English, since learners switch.
- **Instructions** (`instructions`): answer only from the course material (the current lesson, about 4,000 tokens) and what `search_course` finds; outside the courses, one kind sentence and back to the lesson; Egyptian Arabic or English, following the learner; two to four sentences, ending with a check-question when explaining, and another way of explaining after a wrong answer; never give, or say whether the learner is right about, the answer to a course question or the unit check (hints, the idea with another example, the part of the lesson that settles it); no personal data.
- **Graded answers stay out:** a unit check's questions and explanations (lessons `<unitId>-check`, `isUnitCheck`) are left out of the sections, so neither the lesson material nor the search has them; in a unit check the tutor reads the course's readings instead.
- **Where the models run:** Vertex AI in darsi-f0685 (`backend: "vertex"`, the default since 2026-11-03), signed in as the project's service account (`googleToken`, from the Admin SDK's application-default credential), so the cost goes on the project's Cloud billing account and GCP credits apply. Text uses the global endpoint; `gemini-3.8-live` is on Vertex only in us-central1, so voice goes there. `backend: "gemini"` (or `TUTOR_BACKEND=gemini`, which the emulator checks use) is the Gemini API with `GEMINI_API_KEY`, billed from AI Studio's prepaid balance.
- **Typing** (`tutorAsk`), two engines (`config/tutor.engine`):
  - `"direct"` (the default): `gemini-3.5-flash-lite` with the lesson plus the 4 best sections, answering JSON {inScope, answer, sources}. About $0.003 (1.5 credits at $0.002) a question.
  - `"agent"`: the tutor agent below. If it fails, the question goes the direct way, so the tutor keeps answering.
  - Either way, an answer without a known source becomes the fixed "outside your courses" reply (`finish`).
- **The tutor agent** (`agent/`, Google ADK 2.12 in Python, deployed on Vertex AI Agent Runtime in europe-west1 as `darsi-tutor` by `agent/deploy.py`; the gateway is `functions/src/agent.ts`, its pure parts `agentCore.ts`):
  - **Model:** `gemini-3.8-flash` on the global endpoint, thinking level low, for the tutor and its explainer.
  - **Tools:** `search_course` (calls the `tutorSearch` function, so the same index and ranking as the direct engine and the relay), `reply` (in scope or not, and the sources; it ends the turn) and `make_explainer` (an agent used as a tool through `AgentTool`; as a sub-agent it was also offered as a hand-off target, and the model made two explainers in 140 s).
  - **One model call per answer:** the agent writes its answer as text and calls `reply` in the same response. The gateway has already searched the courses, and says so when the search found nothing, so the agent searches again only for a different word. `make_explainer` ends the turn (`skip_summarization`), and the gateway words the chat line from the explainer's first scene: the model call after it only said "it's ready", and once took 55 s to start.
  - **Sessions:** Agent Runtime Sessions, one per tutor panel (`sessionId` goes back and forth), keyed by the uid. The gateway opens each with the state: `tutor_rules` (the same `instructions()` as the direct engine and the voice, so there's one set of rules), `material`, `lang`, `unit_id`, `org_id` and `search_url`. The model only chooses search words; what it may search comes from state. Each question goes with the 4 sections the gateway's own search found for it ("SECTIONS THAT MAY HELP").
  - **What comes back:** the agent writes `reply`, `explainer` and `usage` into session state, so they come back as state deltas on the `:streamQuery` events (`readTurn`). The answer is the tutor's text before `reply`; text before another tool call, and a tool's own output, don't count. `usage` is zeroed when a turn starts and added to by every model call, the explainer's included (thinking counts as output).
  - **Cost** (`turnCost`): tokens at 3.8 Flash's prices ($0.75 / $3.75 per million until 31 Dec 2026, then $1.50 / $7.50: `agentPricesAt` switches on 1 Jan 2027 by itself, and `config/tutor.agentPrices` overrides either; config prices that aren't numbers ≥ 0 are logged and ignored), plus Agent Runtime's compute for the turn's seconds (4 vCPU and 8 GiB at $0.085 and $0.009 an hour). Measured: an answer about $0.002–0.004; an explainer turn about $0.014 (`tutorStatus.explainer` shows it in credits).
  - **A turn that doesn't answer is still charged** (`AgentError`): a turn past its time limit at what it surely cost (its input once and the runtime meanwhile, `abandonedCost`), a reply-less turn or a failed repair at what was measured. `tutorAsk` charges it with the direct answer that takes its place; with no answer at all the learner isn't charged, but the cost is counted.
  - **Time limits:** an ordinary answer may take 8 s and an explainer 75 s (`ANSWER_MS`, `EXPLAINER_MS`) before the question goes the direct way (Flash-Lite, about a second). A question is text only, so it does not wait on an animation. `tutorAsk` allows 180 s and the phone's callable waits as long (`firebase.ts` `SLOW`), so an explainer, its repair turn and the direct answer all fit.
  - **The board:** an animation is made only when the learner asks to see it (Show me, or the voice tool `explain`). The phone shows the board at once with "Let me show you on the board", and the pictures start playing when they arrive. On a call the tutor says that sentence first, then talks through the scenes as they play.
  - **Speed (2026-11-03):** 3.8 Flash is what an answer waits for. With the same questions and rules it took a median of 3.4–4.1 s, with stalls of 29–35 s; Flash-Lite took 0.9 s every time. The user chose to keep 3.8 Flash. Streaming the text wouldn't help: the whole answer arrives within a few hundred milliseconds of the first word.
  - **Warm-up:** the functions and the relay scale to zero, and a cold start cost 3–7 s. When the panel opens, the phone calls `tutorAsk` with `{warm: true}` (that instance loads the course and its index, and opens the agent's session, whose id the phone keeps) and asks the relay for `/warm`. Once per lesson, for Super accounts only; nothing is charged.
  - **Quota:** Agent Runtime allows 30 queries a minute per region for the project (and 10 writes). A question is one query and a warm-up one more; past that the agent answers 429 and the question goes the direct way. More learners need a quota increase.
  - **Eval after the speed work (agent `6058503682603876352`):** 94/104 right and no wrong answers; the 10 others were errors that live goes the direct way (6 over 12 s, 3 quota refusals, 1 turn without `reply`). Median 4.0 s, 90th percentile 7.6 s, $0.40 in all.
  - **Measured (2026-11-03, agent `reasoningEngines/7612245554046697472`):**
    - The eval through the agent passed 102/104: every outside question refused, Arabic 52/52, a median of 4.4 s and a 90th percentile of 9.1 s, $0.0048 a question ($0.498 in all, against $0.146 for the direct engine). Its two misses were errors (a 90 s timeout and one model error) and answered right on a rerun; live, they'd have gone the direct way.
    - Explainers through the gateway: English 30 s and $0.017 (5 scenes, 7.9 KB), Arabic 25 s and $0.016. Both played in the light player at 375 px, the Arabic one right to left.
  - **Who may call:** Agent Runtime doesn't see Darsi's users. The gateway checks the ID token, Super and the credits before every call, and calls the agent as the compute service account. `tutorSearch` answers only a Google ID token made for its own address by `config/tutor.agentAccount` (checked with Google's tokeninfo and cached until it expires; `Bearer emulator` on the emulators).
- **Explainers** (`functions/src/explainer.ts`):
  - **What the agent writes:** flat scenes (`agent/darsi_tutor/explainer.py`): one shape for the templates `title-hook`, `steps`, `flow`, `message-mock`, `quiz` and `summary`, 4 to 6 scenes, the narration in the learner's language and the player's own icons. Free `canvas` scenes stay out until they're checked on phones.
  - **The package:** `toPackage` turns them into Lesson Studio scenes (reveal cues on words actually said, edges only between known nodes, a quiz only with its answer among the options), adds a one-language manifest (`ai` disclosure, brand `darsi-light`) and timing from `estimateTiming`. It then checks the whole package with Lesson Studio's `validatePackage`. A rejected explainer gets one repair turn with the problems, then is dropped. A typical explainer is 5–10 KB of JSON.
  - **The checker's source:** `validatePackage` and `estimateTiming` come from `functions/vendor/lessonstudio-spec.js`, built by Lesson Studio's `scripts/darsi/vendor-spec.mjs`; its types are hand-written beside it. A test checks that the Python schema's templates and icons are ones Lesson Studio knows.
  - **On the phone:** `tutor/Explainer.tsx` plays the package with the light player from memory (`LightLesson`'s `pkg`; nothing is fetched). App passes the player in (`Player`): importing `lesson/LightLesson` from the tutor chunk split startup into seven files. Typing, it waits for Watch and plays silently with captions. In a call it starts by itself.
  - **Show me:** in-scope answers have "Show me" with the explainer's cost. The voice tutor has an `explain` tool (`EXPLAIN_TOOL`): the relay asks the agent, sends `{type:"explainer", pkg}` to the phone, and gives the voice the scenes' narration to talk through. The voice can drift a second or two from the scenes' estimated timing. The relay charges explainers on top of the voice's own cost, one at a time per call. A learner who hangs up before the drawing comes back is still charged for it: the call's held credits are settled and released only after the agent's turn returns (the voice place with them), and a failed one is charged at what it cost (`AgentError`). On SIGTERM the relay waits up to 8 s for those last charges.
- **Talking** (the relay, a WebSocket server on Cloud Run, `node lib/relay.js`): the phone sends `hello` with its ID token; the relay checks Super, credits and the course (side by side where it can), then opens a Gemini Live session while the course's search index builds (`gemini-3.8-live`, voice Kore, the instructions, `search_course`, transcripts both ways, server voice detection with 700 ms of silence). Audio is 8 kHz μ-law both ways (about 64 kbit/s); the phone sends it only while the learner speaks, plus a second of the pause. It answers tool calls itself, sends captions and sources, and closes after 90 s of silence, at `maxMinutes` (14), or when credits run out. Only darsiai.org (and localhost) may connect. `GET /warm?u=<unit>&l=<lang>` answers 204 and warms the settings, Google's token and a public course's index (Cloud Run reserves `/healthz`). Measured from here: Live's first word comes about 1.3 s after the learner stops, a course search included; the relay is in europe-west1 and `gemini-3.8-live` only in us-central1.

A call that cost more than the balance takes what was left. `tutorUsage/{uid}/days/{day}` and `analytics/{day}.tutor` count the cost and credits.

The relay needs `GOOGLE_CLOUD_PROJECT` for Vertex.

## Capstones

Every track's level-3 students' course ends in a capstone unit (`kind: "capstone"`). Its milestones are `project` steps with `evidence` (`repo`, `release`, `check`, `scan`, `url`), a `starterRepo` in the starter organisation (`STARTER_ORG` in `content/capstone.ts`), `hours`, and the `milestone` id the starter's check script reports. Darsi never runs what a learner builds: the evidence is their own GitHub Actions run and the `darsi-check.json` their copy of the starter wrote, both claims a person still reviews.

- **Shape:** three lessons (stages): the description, the starter (readings: how to set up, with `setup` tabs for Windows, Mac and Colab/Codespaces in the browser, so the work runs on the learner's own computer or a free cloud notebook) and the submission (a reading, then the milestones `m1`…). Nothing in a capstone is graded: no quizzes and no score (its lessons count as done, not scored: see "Graded lessons only" in [Organization analytics](#organization-analytics)). `tests/units.test.ts` skips the question-mix and six-slide rules for capstones (at least three slides; their kits print the milestones), and the validator allows milestone fields only in a capstone (`capstoneOnly`). The certificate needs every milestone sent, and Home moves nobody up for an unfinished capstone ("Cloud sync").
- **Writing one:** docs/CONTENT.md "Capstones". The starter repositories are in `STARTER_ORG` (https://github.com/darsi-org); the course text is Egyptian Arabic, like the videos.

- **Coming back:** a milestone sent from this phone keeps the time, the submission's id and the account that sent it in its draft, so for that account it opens as sent ("Sent on …", with "Improve it and send again"), and the submission lesson opens at the first milestone it hasn't sent yet (`nextMilestone` in `screens/LessonScreen.tsx`); on a shared phone, another account starts afresh. Its heading is the prompt's first paragraph ("Milestone N: title"); the card shows the task and what to send. A milestone that needs a link says so while the links box is empty.
- **Sending** (`lesson/ProjectView.tsx`): a milestone goes through the `checkCapstone` callable (`functions/src/capstone.ts`; the pure parts, tested, in `capstoneCore.ts`). It writes the submission with the Admin SDK, so learners can't set `checks`, `aiReview`, `queue` or a status. Learners in a school go to their teacher (`queue: "teacher"`); the others to Darsi staff (`queue: "staff"`, /super/projects). A send refused for what it is (not-found or failed-precondition: not a capstone milestone; invalid-argument: input `parseInput` refused) says so (`refusal`: `closed`, `invalid`) instead of blaming the connection, and keeps the draft. Files go up first; only addresses in the learner's own folder are kept (`filesPrefix`: the object's address without a token, the same form on the emulators), and a refused send deletes the files it put up, since nothing was written. The setup tabs' `<mN>` shows as the milestone's id.
- **Limits first**, in one transaction over `capstoneLimits/{uid}` and `capstoneDays/{day}`, before any GitHub request or model call (`allowance`):
  - one send per account every 20 s (`capstone-wait`) and `config/capstone.callsPerDay` a day (default 20; `capstone-limit`). Both are `resource-exhausted`; the phone says which (`refusal` in `lesson/capstoneText.ts`) and keeps the draft;
  - AI reviews: `perDay` per learner (default 5) and `maxPerDay` for the whole platform (default 300; a warning is logged at 80% and at 100%). Over either, or with `ai` off, the review is `skipped` and the work still goes to a person.
- **Checks** (`runChecks`), from the milestone's `evidence`: the repository is there and public (`repo`), its latest GitHub Actions run passed (`ci`), it has a release tag (`release`), darsi-check.json is this track's and passed the milestone (`check`), every scan in it targeted only localhost (`local`; always for aisec and cyber), links were given (`links`).
  - Each is passed, not passed, or **not checked** (`ok: null`): what GitHub didn't answer (a rate limit, its own error, a timeout) is "not checked, send it again later", never the learner's failure, and the AI reviewer is told NOT CHECKED.
  - The starter repository itself (its owner is the starter organisation) is refused without asking GitHub.
  - darsi-check.json is bounded (`parseCheck`): at most 12 milestones, 40 checks each, and 40 metrics whose names start with a letter or digit (`METRIC_KEY`; Firestore refuses `__…__` field names, which would fail the write after the review).
- **GitHub** (`repoFacts`): three requests per send (the repository, its latest run, its newest tag) with Darsi's own token, the `GITHUB_TOKEN` secret: a fine-grained token with read-only access to public repositories, so GitHub allows 5,000 requests an hour. `unset` means none; GitHub then allows 60 an hour per address, shared by every instance behind it. Answers are kept per instance (`factsTtl`): 5 minutes for a passing, tagged repository, 1 minute for anything a learner may be fixing, never a partial answer.
- **The AI review** (advisory; `reviewPrompt`, `parseReview`, `capScores`): the tutor's text model (`config/tutor`, Vertex AI by default) scores each rubric criterion 0–3, in English and Arabic.
  - Only Darsi's own words sit outside the work: the course, the task, the rubric, and the checks as fixed ids with PASS, FAIL or NOT CHECKED (never their texts, which carry learner and GitHub strings).
  - Everything the learner sent is one JSON value inside a fence named `work-<12 random hex digits>`, new for every review: their text, explanation, AI use, repository, links, and the ids, true/false values and numbers from their check file (never its words). Anything in it that looks like the fence is defused, so the work can't close it or speak as Darsi.
  - A failed check caps every score at 1 in code (`capped: true`), whatever the work talked the model into; the screens say so. They label the whole box "AI review (a suggestion; a person decides)".
  - The milestone is named from its own step (`milestoneOf`: the first line of its prompt, "Milestone 1: …", and the number from its id `m1`), never from the lesson that holds every milestone ("3. Project submission", which made the model call milestone 1 «المرحلة الثالثة»); the model is told to call it «المرحلة ١» in Arabic.
- **Arabic in checks and reviews:** a Latin or code token in a check's Arabic (a milestone or check id, darsi-check.json, a tag, a scan target) sits in a left-to-right isolate (`ltr`, with the token's own direction controls dropped), and no Arabic sentence ends on one: on a right-to-left page its full stop shows on the token's other side (".m1"), so those sentences are worded with the Latin earlier. The model is asked the same, and `parseReview` isolates the Latin and code runs in its Arabic (`isolateLatin`, which also drops the model's own direction controls).
- **Settings and cost:** `config/capstone` {ai, perDay, maxPerDay, callsPerDay} changes only through `saveCapstoneConfig` (platform admins; audited; `CAPSTONE_BOUNDS`), from "AI reviews of capstone milestones" on /super/plans (`admin/CapstoneSettings.tsx`, with today's reviews and cost). The day's use is in `analytics/{day}.capstone` {calls, reviews, usd} and `capstoneDays/{day}` {n, usd}. A review costs about $0.001 on Flash-Lite (up to about $0.005 at Flash prices), so the default platform budget is at most about $1.50 a day.

## Code on the phone

Lessons can teach code: `code` (write and run Python or SQL, graded by tests), `parsons` (order and indent lines), `codefill` (gaps), `bug` (find the line) and `blocks` (a robot programmed with command cards, for young learners), plus `snippet` on any question. docs/CONTENT.md says how to write them.

- **Runtimes** (`public/lib/python/v1`, `public/lib/sql/v1`; `scripts/vendor-runtimes.mjs` copies them from the pinned npm packages):
  - MicroPython 1.29.0-6, the PyScript variant's `settrace-ulab` build: real Python 3 syntax, `ulab` (numpy-style arrays), `sys.settrace`. About 0.29 MB gzipped.
  - sql.js 1.14.2 (SQLite 3.49.1): about 0.34 MB gzipped.
  - Each is downloaded the first time a lesson needs it (its size shown first), cached in `darsi-lib` (kept when a unit is removed) and never precached. `content/runtimes.ts` lists the files and sizes; a downloaded unit includes its runtimes, and the catalog's size counts them.
  - The vendoring step adapts MicroPython's loader, and stops if any change doesn't apply exactly once (check it on a version bump): the heap may grow only to 48 MB (`globalThis.__mpHeapMax`), it takes a compiled module (`instantiateWasm`) instead of fetching, and it is a classic worker script rather than an ES module.
- **The sandbox** (`src/code/sandbox.ts`):
  - A hidden `<iframe sandbox="allow-scripts" srcdoc>` has an opaque origin: no cookies, storage or IndexedDB (so no sign-in tokens), and no access to the page. Its CSP is `default-src 'none'; script-src 'unsafe-inline' 'unsafe-eval' 'wasm-unsafe-eval' blob:; worker-src blob:; connect-src 'none'` (`'unsafe-eval'` for Chrome before 97). **Any CSP added to the app later must still allow this iframe.**
  - Inside, one blob worker per language. It deletes `fetch`, XHR, WebSocket, IndexedDB, `caches`, `navigator` and `importScripts` before the runtime starts; MicroPython's `js`/`jsffi` modules are set to `None` as well.
  - The iframe compiles each runtime's wasm once and hands the module to every new worker.
  - The page enforces a 3 s limit (`TIME_LIMIT`): it ends the worker and starts a fresh one (15–50 ms). Stop does the same. After a minute without a run, everything is removed (battery and memory).
  - Checked in Chromium 153, Firefox 157 and WebKit 27: storage and the parent are blocked, `fetch` is refused, an endless loop stops on time.
- **The harness** (`src/code/harness.ts`), shared by the sandbox and the Node tests so a solution is graded the same way everywhere:
  - Python: `_darsi_run(json)` runs the program once per test with fresh variables, its own `print` (captured; output and graded text capped at 20 KB) and `input` (the test's answers), a virtual clock (`time.sleep` returns at once), then the test's `check`. Tests compare only printed output. Any exception, `MemoryError` included, is caught in Python; the program's objects are freed before the traceback is formatted (with the learner's line, long ones shortened). It also provides a small `csv` module.
  - MicroPython keeps every interned string (`str(i)` makes one) for good, so after a run that leaves more than 8 MB in use the interpreter is started afresh (`HEAP.restart`). A program that makes millions of small objects near the cap slows the GC to a crawl; the time limit ends it.
  - SQL: `runSql` runs the query on fresh tables and compares its rows with the solution's (`sameRows`). The worker carries `runSql`, `sameRows` and `isOrdered` as source (`toString()`), so they must stay self-contained.
- **The Python library** (`src/code/pylib/*.py`, imported as raw strings by `pylib.ts`, written to MicroPython's `/lib` when it starts):
  - `csv`.
  - **Darsi's small OR-Tools**, in Python, shaped like Google's so programs run unchanged on the real thing:
    - `ortools.sat.python.cp_model`: integer domains, linear constraints, all-different (over expressions too, through helper variables), bool_or and implications, a linear objective; depth-first search with bounds propagation, branch and bound, solution callbacks and enumeration; a node limit.
    - `ortools.linear_solver.pywraplp`: a two-phase simplex with Bland's rule for LP, and branch and bound for whole numbers.
    - Pure Python rather than TypeScript behind a JavaScript bridge: nothing more to ship into the worker as source, the same in the Node tests, and readable by learners. The Labs apps keep their own TypeScript models.
    - `tests/code/ortools.test.ts` runs Google's guide examples (the first CP-SAT model; the optimisation example, 35; SEND+MORE=MONEY; eight queens' 92 solutions; the first LP, 4; the LP example, 34; the MIP example, 23; the assignment example, 265) in under a second.
  - **`machine`, the virtual board** for IoT: `Pin`, `ADC`, `PWM` on board time. The harness's sleep raises `_TimeUp` past the step's `seconds`, which ends the run without an error; every pin change is recorded (at most 2,000) and returned as `board` with the run, and `BoardView` (CodeSteps) plays it back at 4× (at once with reduced motion). `utime` is mapped to the harness's `time` (MicroPython's own `utime` keeps the real clock).
- **What a phone keyboard types** (`normalizeCode` in `code/harness.ts`, run by `CodeSteps` before every run and shown in the editor, so the learner sees what ran): outside strings and comments, Arabic-Indic and Persian digits become 0–9, the Arabic comma, semicolon, decimal point and percent sign become `, ; . %`, wide spaces become spaces, direction marks and zero-width characters go, « » around a value become a string's quotes, and curly quotes become straight ones. Strings and comments keep what was typed (`print("٣، ٤")` still prints Arabic digits). Code with nothing outside ASCII is left as it is. `tests/code/normalize.test.ts`.
- **Chunks:** the five step views are the lazy `CodeSteps` chunk (`src/code/loader.tsx`; strings inside it, en/ar) and the sandbox is the `sandbox` chunk (shared with the editor). Both are left out of the precache; downloading a unit with code fetches `CodeSteps` too. `CodeBlock` and the highlighter are startup code (questions' snippets).
  - **Bundle rule, again:** `content/runtimes.ts` is used by startup code and the lazy chunks, so it has type-only imports. When it imported a value from `content/types.ts`, Rolldown moved React, the design system and i18n out of the entry (5 startup files).
- **Robot:** `content/robot.ts` (pure, copied to the functions) runs a program for the engine and the view and finds the fewest cards for the validator.
- **Editor:** `cms/codeForms.tsx`, with "Run the tests" (the solution must pass, the starter must not) in the same sandbox.
- **Tests:** `tests/code/harness.test.ts` (the harness in the real runtimes, via `tests/code/node.ts`, which hides `process.argv[1]` while importing MicroPython's loader or it starts a REPL on stdin), `steps.test.ts` (grading, validation, robot, colouring), `views.test.tsx` (each view, sandbox mocked), `tests/units.test.ts` (every course's code steps), and `e2e/code.spec.ts` (the real sandbox in the built app).

## Darsi Tiny (an agent model on the phone)

Four models, each 2.94 M parameters and about 3 MB. Two are for the labs and two are for live teaching. One of each job is English and one is Arabic, so a phone downloads only the language on screen.

- **Apps** (`/lib/tinylm/app/en/v2/`, `/lib/tinylm/app/ar/v2/`): text and tool calls. A request, a plan, one school tool, the result, an answer. They passed a held-out eval per language, but no lab runs them yet: the agents and AI security labs, their tries, recorded runs and lessons were written against the shipped bilingual model at `/lib/tinylm/v1/`, and v2 behaves differently (decided 2026-11-06 for the security labs, as for the agents labs on 2026-11-04: v2 Arabic refuses the guardrails scam outright, privilege's attacks act on other scenarios, and the red team's misses change). Moving a lab family to v2 means re-measuring and rewriting its tries, recorded runs and lessons first (`tests/labs/aisec.test.ts` pins what they promise).
- **Teaching** (`/lib/tinylm/scene/en/v2/`, `/lib/tinylm/scene/ar/v2/`): the tutor only. The model writes a compact scene (a few names and numbers), reads the result computed by the phone, then explains it. The phone expands the JSON into a Lesson Studio pack and the player draws every frame from the clock, so a new question is a new animation and no video is downloaded. `apps/web/src/labs/apps/tutor/expand.ts` is that expansion.

**Shared v2 architecture.** Every model has 2,937,792 parameters: language-specific byte BPE (3,000 tokens), tied embedding/output head, width 192, six pre-norm decoder blocks, six 32-dimensional query heads with two shared K/V heads (3:1 GQA), RoPE, and a 512-wide SwiGLU FFN. Weights are row-wise int8; activations and norms are float32. The runtime has a real token-by-token KV cache, reuses a prompt's shared prefix after every tool result, fuses SwiGLU's two input projections, streams in batches, and ends its worker when idle. GQA reduces the full 384-token cache from 3.375 MiB to 1.125 MiB. The v1 MHA + GELU format remains readable.

The architecture was selected by equal-size ablation, not by fashion: 7×192 GQA and 8×160 MQA candidates were trained and compared with the 6×192 GQA candidate. The six-layer candidate had the best validation/eval result and the best slow-CPU latency. Browser measurements compare fixed prompt/decode work and PyTorch token parity. This is Darsi's best measured 3 M-parameter configuration; “global SOTA” is not claimed without a public benchmark at this unusually small scale. BitNet was rejected because ternary speed depends on specialized native kernels and is not a browser win.

For the AI agents and AI security lessons the shipped model is a 2.94 M-parameter decoder-only transformer, int8, with a 3,000-token byte-level BPE for English and Arabic and a 384-token context, trained on this PC from synthetic bilingual agent episodes. It reads a request, writes a short plan, calls one of ten simulated school tools, reads the result and answers; it asks when something is missing, asks for approval before sending a message, refuses, says "I can't" for anything its tools don't cover, and ignores instructions inside tool results. It is not generally smart: the lessons use that to show why large models are large and how to evaluate and guard an agent. `tools/tinylm/README.md` has the commands, `MODEL_CARD.md` the data, evaluation and limits, `FORMAT.md` the format.

- **V2 gates** (2026-10-31): app models, right tool and exact arguments on held-out names 100.0% English and 98.4% Arabic; OOD rewordings 84.8% / 79.6%; later-written fresh wordings 64.0% / 56.3%; blind wordings 44.3% / 55.9% (the honest limit). The teaching suite has 600 cases per language. The deterministic validator/course-pack router passes 600/600 each; raw int8 teaching models achieve **100.0% / 100.0%** valid scene JSON or refusal, **96.8% / 97.8%** exact scene parameters, **100.0% / 98.8%** plain explanations, and **96.8% / 97.7%** all checks (100% on parameterized, pack concepts, follow-ups, and refusals) while using ~50% fewer tokens per turn (`<|plan|><kind>` + 1-sentence explanations). Fixed-work Chromium: 76 tok/s median and 73 slowest at 6× CPU throttle, 679 tok/s unthrottled, 429 tok/s through the real worker. The same tokens as PyTorch on 12 v2 prompts, logits within 1e-4; v2 fine-tuning gradients match within 1e-3. `MODEL_CARD.md` holds the full tables and caveats.
- **On the phone:** `src/tinylm/` (plain TypeScript, no libraries; only a lab chunk may import it, through `index.ts`): `TinyLM` with `load()`, `generate(conversation, { onToken })`, `stop()`, `finetune(examples, { steps, blocks, replay })` and `useFineTune(saved)`; `fetchManifest()` gives the download size first; `runTool(world, tool, args, lang)` runs the simulated tools over `world.json`. It runs in a Web Worker that starts on the first call and ends after 5 s without work. The files are in `public/lib/tinylm/v1/` (2.75 MB gzipped), kept by `darsi-lib` once used; a new model goes in `v2/`.
- **Fine-tuning in the browser:** only the top one or two blocks and the final norm train (the rest stays int8). Without replay it forgets everything else (97% → 14%), so `finetune` mixes in ordinary conversations from `replay.json` (48 keep 95%). About 0.7 s per example per step on a 6×-slow phone: keep a lab to about 16 examples × 15 steps. The `teach` lab does exactly that: on a PC it takes 38 s with no replay and 2 min 16 s with 48 (about 11 minutes estimated on an old phone), and replay 48 keeps every old skill (8/8) where none keeps 1/8.

## Authored content

The course editor lets **platform admins publish units for everyone** (guests included) and **org admins publish units for their own organization's members**. It edits full units: every step type, slides, competencies and uploaded media (an MP4 and VTT captions per language, plus kit PDF/PPTX files). It is the only way courses reach learners: the app ships none.

**Flow.** Drafts live in Firestore (`units/{id}` holds the light record lists read; `unitDrafts/{id}` holds the content), saved 3 s after the last change and with "Save draft" or Ctrl+S (see "Autosave" below). "Publish" saves, then calls `publishUnit`. Only the functions write what learners read.

**Ids.**
- New units: `u` + 8 random characters (`[a-z0-9]`). Org units must use this form (`idFits` in the rules, `idAllowed` in `functions/src/catalog.ts`).
- A platform admin's import keeps the unit's id (`ai-1.json` stays `ai-1`), so a unit exported from the editor comes back as itself with its learners' progress. `npm run seed` keeps the starting courses' ids the same way.
- Lesson ids are `<unitId>-` + 4 random characters and are never reused. Progress, notes and kit anchors are keyed by lesson id, so deleting a lesson and adding another can't hand someone's old progress to the new one.
- Step ids (`choice1`, `video2`, …) only need to be unique within a lesson.

**Validation** (`apps/web/src/content/validate.ts`): pure, dependency-free, and takes `unknown`, so pasted JSON can't crash it.
- **Errors** block publishing. They are everything that would crash a lesson or leave it stuck: an answer missing from the options, fill-in blanks that aren't numbered 0…n-1 or whose answers aren't each once in the word bank, hotspots outside the stage, unsafe media links (only `https:`, `/media/` and `/kits/`), duplicate ids, a lesson over 300 KB or a unit over 600 KB.
- **Warnings** don't block: a missing translation (`missingLang`, for Arabic or the languages the editor shows), unknown competency codes, no slides.
- **Track and level:** with the `tracks` option (track id → number of levels), the track must be one platform admins set up and the level must be one it has. Without it, any well-formed id (`[a-z][a-z0-9-]{1,23}`) and levels 1–12 pass. The editor and `publishUnit` both pass the saved tracks.
- `functions/scripts/copy-shared.mjs` (npm `prebuild` in `functions/`) copies `types.ts`, `validate.ts`, `tracks.ts`, `languages.ts`, `robot.ts`, `runtimes.ts`, `capstone.ts`, `orgCourses.ts` and `sites.ts` from `apps/web/src/content/` into `functions/src/shared/`, and writes `labs.ts` (every Labs app id, from the `meta.ts` files) for `collect`. The copies are committed, and a functions test fails if they drift from the web source.

**Storage layout** (`functions/src/catalog.ts`, pure and unit-tested):

```
content/settings.json                  tracks and languages: { version, tracks, languages }, max-age=60 (saveSettings, publishLanguage)
content/sites.json                     organization sites: { v, sites: { host: { orgId, name, logo, darsi } } }, max-age=60 (setOrgSite, onOrgSite)
content/sites/{orgId}/{hash}.{ext}     a site's logo, copied from orgs/{orgId}/brand/ (members only) so anyone can read it, immutable
content/i18n/{code}/v{n}.json          a published language's UI strings: { code, version, messages }, immutable
content/catalog.json                   public units: { version, units: CatalogEntry[] }, max-age=60
content/units/{id}/v{n}.json           one file per published version, immutable (the current and previous version are kept)
content/media/{id}/…                   uploaded videos, captions and kit files
orgs/{orgId}/catalog.json              the same for one organization, readable by its members only
orgs/{orgId}/units/{id}/v{n}.json
orgs/{orgId}/media/{id}/…
```

Every JSON file the functions publish (catalogs, units, settings, plans, language packs) is stored gzipped with `Content-Encoding: gzip` (`saveJson` in `functions/src/storage.ts`), and so are the seed's `.json` and `.vtt` media (the light lessons' scenes, timing and captions; a copy stored before that is uploaded again): browsers ask for gzip and unpack it themselves, so phones fetch 3 to 8 times fewer bytes for the same `fetch().json()`. A unit's JSON size in `sizeByLang` is its gzipped size.

Each catalog entry carries `src` (the JSON's Storage path), `version`, `owner`, `sizeByLang` and `sizeMB`. `sizeByLang` is what a download fetches in each language (`sizeByLang` in `functions/src/catalog.ts`, mirroring `unitAssetUrls`): the JSON, each video step's light lesson (or its MP4 when it has none), the kits' files (not video kits), the pictures in the text and the code runtimes. A language without its own file counts the English one, as the app does. `sizeMB` is the largest language, for phones that don't read `sizeByLang`; Downloads shows the learner's own (`downloadMB`). Kit files carry `sizeKB` (language → format → KB, like `urls`): the seed records it from the files on disk (`withKitUrls(…, { sizeOf })`), and the editor records it on upload. Before 2026-11-05 kits weren't counted, so courses showed about half their real size. Media links in a lesson are Storage download URLs, so `<video src>` plays without headers. For org media they are bearer links: anyone given the link can open the file. Uploaded files get a unique suffix, so replacing a file never breaks the link inside an already-published version.

**Loading** (`apps/web/src/content/load.ts`):
- `loadCatalog()` merges two catalogs:
  1. the public catalog, fetched with **plain `fetch`** from the Storage REST URL, so guests never load the SDK;
  2. for org members, the org catalog.
- `mergeCatalog`: public entries first, then the org's; an org entry never replaces a public one.
- The Vite dev server only (`import.meta.env.DEV`, not in tests) also merges `/content/dev-catalog.json`, and serves each listed unit from `content/units` at `/content/dev/<id>.json` (both from the `devUnits` middleware; the list itself is `content/dev-catalog.json` at the repository root, written by `scripts/build-arch-courses.mjs`, so it never ships or goes into the precache). A public catalog it cannot read counts as empty, so a local course still opens. Tests and builds, including a build served on localhost, never request the file.
- Nothing published yet (a 404) is an empty catalog, and Home says "No courses yet". No answer and no copy from an earlier visit (a first visit offline) is an error, and Home offers Retry. A unit missing from the catalog can't be loaded: there are no built-in files to fall back on.
- **Caching.** Catalogs are network-first with the last copy as the offline fallback. Unit files are cache-first by their versioned path. Both live in `darsi-content`, managed here rather than by a service-worker rule (a stale-while-revalidate rule would serve old catalogs and store everything twice).
- **Org files** go through the SDK (`storageJSON()` in `firebase.ts`). App hands load.ts the reader with `setOrgReader` (see "The bundle rule" below).
- **Scope.** App calls `configureContent({ orgId, signedIn })` on every render. A change re-reads the catalog. Signing out deletes every cached org file (shared phones): a `darsi:orgFiles` flag in localStorage says whether there are any.
- **Downloads:** `unitAssetUrls(unit, lang, entry)` leaves an authored unit's JSON out (loadUnit already cached it), and adds its uploaded kit files, video and captions. `cacheNameFor` routes Storage JSON to `darsi-content` and other Storage files to `darsi-media`.
- `videoSrc(step, lang)` and `kitUrl(file, lang, fmt)` in `content/types.ts` resolve uploaded files (`sources[lang]`, `urls[lang][fmt]`, falling back to English, then to any language) and the older `{lang}` templates.

**The bundle rule (learned the hard way).** A module shared between the startup bundle and lazy chunks (`content/load.ts`, the lesson player…) must not import the Firebase SDK or anything that lazy-loads it, **not even dynamically**. Otherwise Rolldown splits the startup bundle into several files: 7 instead of 2 when this was measured, with more requests on a first visit. That is why:
- App passes the org reader in (`setOrgReader`);
- App passes the lesson player in (`<UnitEditor Player={LessonPlayer} />`) instead of the editor importing it;
- the editor has a single lazy entry module (`cms/Cms.tsx`);
- App registers the light-lesson player (`setLightPlayer`), a lazy chunk that imports nothing. A new lazy chunk that imports React or `content/load` can split startup too (six files when measured on 2026-10-27), so measure every new one.

Manual `codeSplitting` groups capture their dependencies recursively (a `src/cms` group once pulled React, the router and the design system into the editor chunk and loaded it at startup), so never add one for app code. To check, build into a separate folder and follow the entry chunk's static imports: they should stay at `index` + `rolldown-runtime`. Measured on 2026-10-26 with the Labs apps in the tree, the entry also imports `dist` (`@capacitor/core`, 7.8 KB) and `preload-helper`: 4 files, 152 KB gzipped (155 KB on 2026-10-27, with languages and light lessons). Builds without Labs stay at 2 files, so the split came in with Labs. It is accepted for now: the total size is the same, and it must not grow past these four.

**Old Android phones (Chrome 61+).** `@vitejs/plugin-legacy` keeps that modern build for browsers with `import.meta.resolve` (Chrome 105 and newer) and writes a second set of chunks, transpiled to Chrome 61 and polyfilled, for the rest. The legacy files are not precached (`*-legacy*` in `globIgnores`); `darsi-chunks` stores them when an old phone asks. The modern entry must still be four files: the plugin's guard is text inside the entry, not another file, and `modernPolyfills` stays off. `index.html` registers `/sw.js` as the page is parsed (the update toast still loads `workbox-window` later, with `immediate: true`; its Reload is `takeUpdate` in `pwa.tsx`, which reloads when the new worker activates or takes control, after 4 s whatever happens, and at once if nothing is waiting, because a page the worker doesn't control never sees it take over) and shows a light, bilingual "please update your browser" note only if `#root` is still empty after 15 seconds. MicroPython and sql.js ship a `.legacy.js` beside the original, because those files are classic scripts the legacy build does not see; the sandbox and downloads pick it when `?.` fails to parse. The video bar and the app bar use margins rather than flex `gap` (Chrome 84), and the app-bar title sets `min-width: 0` as well as `min-inline-size: 0` (Chrome 83). The manifest has no `purpose: "monochrome"` icon: older Chrome rejects it and will not install. CSS stays targeted at Chrome 111. Lowering it to Chrome 61 rewrote logical margins into a broken language hack, and Chrome 69 already understands the logical properties these styles use.

## Tracks and levels

Every unit belongs to one **track** (one of the nine built in, or one a platform admin added) and one **level** of that track. Platform admins manage the tracks at `/super/tracks`; every unit uses the same list, org units included.

**Model** (`content/types.ts`, `content/tracks.ts`): `TrackDef { id, name, summary?, icon, tone, levels (1–12), levelNames?, order, hidden? }`.
- Nine tracks are **built in** (`BUILTIN_TRACKS`): `ai`, `iot`, `cyber`, since 2026-10-28 `code` (Programming), `data` (Data engineering), `agents` (AI agents), `opt` (Optimization) and `aisec` (AI security), and `data-science` (Data science; its unit ids start `ds-`). The first eight each have their own tone (the eight tones) and icon (`code`, `chart`, `agent`, `peak`, `aisec` for the newer ones); Data science shares IoT's `lagoon` tone, with the `target` icon. Tracks admins add share the tones. They can be renamed, hidden or given more levels, but never removed or recoloured: Labs, placement and the shipped units use them. Labs has shelves for each (`labs/categories.ts`); a shelf or a track chip shows once it has apps. `mergeTracks()` applies that rule wherever a saved list is read (the app, the editor and the functions).
- `tone` is one of 8 brand colour families. `sunbird`, `lagoon` and `hibiscus` came with the first three tracks; `leaf`, `lilac`, `clay`, `sky` and `slate` were added for new tracks and now belong to the five built-ins of 2026-10-28. Each has a solid, `-soft` and `-ink` token in both themes, and `check-contrast.mjs` checks them (ink on solid and on soft, `-ink` on soft, surface and paper). `icon` is any design-system icon; the Tracks page offers 18 subject icons.

**Where it lives.** `config/settings` in Firestore is the source of truth, and `saveSettings` alone writes it.
- `saveSettings` is for platform admins only. It validates the list (`validateTracks`: ids, names, colours, icons, 1–12 levels, built-ins present).
- It refuses a save from an older `rev` (`aborted`), so two admins can't overwrite each other.
- It refuses changes that would strand a unit (`failed-precondition`, with `conflicts`): removing a track that any unit uses, or lowering a track's levels below a level in use. Drafts and org units count (`trackConflicts` in `functions/src/trackRules.ts`).
- It then writes `content/settings.json` (public, `max-age=60`).

**In the app** (`content/settings.tsx`):
- `SettingsProvider` sits inside `I18nProvider`. It starts from the built-in tracks, so nothing waits or flashes, and switches to `content/settings.json` when it arrives. The file is read once per app start by `loadSettings()` with a plain `fetch` (network-first, last copy offline, like the catalogs), so guests never load the SDK.
- It also gives the design system each track's tone and icon (`TrackStylesProvider`).
- `useTracks()` returns `all`, `visible` (not hidden), `of(id)`, `name(id)`, `levelName(id, n)` and `order(id)`. A track nobody set up (deleted, or content from elsewhere) shows neutrally under its id, in slate with the `learn` icon.
- **Design system:** a track's colours come from `dr-tr dr-tr-<tone>`, which sets `--tr`, `--tr-soft` and `--tr-ink`. Chips, progress bars, the unit path, certificates, placement results, page previews and download rows read those variables. Components still take a `track` id and resolve it through the provider (`useTrackStyles`, `trackClass`).
- **Where tracks show up:**
  - **Onboarding** offers the visible tracks, then the placement check (`PlacementQuiz` in `screens/Onboarding.tsx`) for the learner's tracks and audience only. Per track it asks two questions per level (picked at random from three); both right passes a level, and a wrong answer or "I don't know yet" misses it (`placementNext`). It starts at the learner's school stage (where a teacher teaches, or where a student studies). From there a pass moves up until a level is missed (the learner starts there) or the top is passed, and a miss at the start moves down until a level is passed (the learner starts one above it) or the lowest is missed. A track without questions starts where the learner starts.
  - **The check places only where there are courses** (`placeLevels`, `placeStart` and `usePlacement` in `content/mine.ts`), so its result is the level Home then shows as "Your level". It walks only the levels with a published course for the learner in that track (their audience; university courses for university teachers), and a student goes no higher than their own stage (courses are written for a stage; the lowest level with a course if nothing is at or below it). It starts at the learner's level among those, or the nearest above. A track left with one level asks nothing, and the result says no questions were needed. With no catalog (offline) or no course for them in a track, every level up to that cap. The result's levels are what "Start learning" saves, for every chosen track. Closing the check goes back to the step where it can be skipped.
  - **Stages:** levels are school stages: Beginner is primary school (ages 9–12), Elementary lower secondary (12–15), Intermediate upper secondary (15–18) and Advanced university. Onboarding asks students "Where do you study?" (school accounts too), saved as `state.stage`. It asks every teacher, including a school's teacher accounts, "Where do you teach?" (primary, lower secondary, upper secondary, or university). That is saved as `state.teach` (the same four values; the old `secondary` answer is read as lower secondary) and changeable in Me ("Where I teach"). `useMine()` gives `startLevel`, `levelOf` (the level, else the start), `levelName` (the learner's level: "Your level", the check's result, My levels; for students on built-in tracks with their own stage beside it, "Intermediate · Upper secondary", and never another stage, which isn't theirs) and `courseLevelName` (a course's level, with the stage it is written for). Home starts a teacher at that level and folds earlier courses under "Earlier levels"; courses tagged `teach: "university"` stay visible only to university teachers, pinned first. At the top level, a university teacher's "Your level" is that university course, and the school course at that level (school leadership) folds under its own name ("Also at your level, for school teachers"), not with the earlier levels. Folds start closed again on another track. Past the weekly goal, the week card says the goal is met with the count, not "5 of 4". Tracks are not hidden: every track has a teacher course at each level. Both questions (and Me's) offer only stages with a published course for that audience in a visible track (`stagesWithCourses` / `useStagesOffered` in `content/mine.ts`): students' courses at the stage's level, teachers' courses at that level, and for university teachers the university courses too. A stage whose courses are all unpublished disappears; with no catalog (loading, offline) or no courses at all, every stage is offered. Guests keep `teach` in local storage. Signed in, it is part of the learning profile on `users/{uid}` (with `stage`, `audience`, the tracks and levels; see [Cloud sync](#cloud-sync)), copied by `useLearningSync` in `App.tsx`, which loads Firestore only for a signed-in account.
  - `tests/placement.test.ts` checks `placement.json` (version 5): it covers every built-in track and every question of `content/placement/<track>.json`, with three questions per audience and level, plus three `teach: "university"` questions for teachers at the top level, asked only of university teachers (two of them, as at any level), in English and Arabic, with no "·".
  - **Levels have names:** the built-in tracks' `levelNames` are Beginner, Elementary, Intermediate and Advanced (`LEVEL_NAMES` in `content/tracks.ts`); `mergeTracks` keeps them for a built-in track saved without names.
  - **My tracks** shows each track's level with "Check my level" (the same check for that track only), and offers it when a track is added.
  - **Home** starts at the learner's level (`startAt` in `screens/Home.tsx`): the course at their level first ("Your level: …"), the levels above in order, and the earlier ones folded under "Earlier levels" (open, with a note, when nothing exists yet at or above their level). Finishing the course at your level moves `state.levels[track]` up one (a capstone only once its milestones are sent). Courses come in the order they are taken (`byOrder`: by level, a capstone after its level's other courses, then by id with numbers counted as numbers, so `ai-u1` … `ai-u4`), whatever the catalog's order; the pinned university courses too. Only the first course on the page loads at once; the others load as they come near the screen (`Near`, an IntersectionObserver), and folded ones when the fold is opened. A course that can't load says so, with Retry, and tries again when the connection returns.
  - **Home** shows **one of the learner's tracks at a time** (`content/mine.ts`: `useMine`, `myTracks`, `activeTrack`). The current track is a switcher in the app bar (`components/TrackSwitch.tsx`); its menu lists the learner's tracks and "Add or remove tracks". Ready units first, then by level. A track with nothing for the learner says so, with a link to My tracks.
  - **My tracks** (`/tracks`, `screens/MyTracks.tsx`): every visible track as a choice card with its number of courses for the learner's audience. Adding a track makes it the current one; removing one keeps its progress; at least one stays. `state.tracks` holds the choice (none chosen means every visible track) and `state.track` the current one.
  - **Kit and Downloads** list the learner's courses: their audience, in any of their tracks.
  - **Me** shows "My tracks" (with "Add or remove tracks"), "I am" (a teacher or a student; not for school accounts), "Where I teach" or "Where I study", and "My levels" out of each track's own number of levels, with level names when set.

**Courses for teachers or for students.** Every unit has an audience: `audience: "students"`, or none for teachers (every course before audiences existed). Students see only courses for students and teachers only courses for teachers, in the same tracks.
- **Who is who:** school accounts follow their role (`student` → students, `teacher` → teachers); everyone else answers "Who are you?" in onboarding (a teacher or a student) and can change it in Me (`audienceFor` in `content/mine.ts`). A teacher then chooses where they teach; that choice is what `startLevel` uses.
- **Editor:** "Who is it for?" (Teachers / Students) in a unit's details; the list marks courses for students. `units/{id}` keeps `audience` for the list (rules allow the field).
- **Published:** `catalogEntry` adds `audience: "students"` to the catalog for courses for students only; the validator accepts `teachers` or `students`.
- 48 of the 96 course sources are for students (30 of them live on 2026-11-07). A student's track with nothing published for students says "Courses for students in … are on their way".
- **Order:** `publishUnit` writes catalogs in the saved track order (`buildCatalog(entries, order)`; unknown tracks last).

**The Tracks page** (`cms/TracksPage.tsx`, in the `Cms` chunk). It reads `config/settings`, plus every unit's track and level, once.
- One card per track, in order, with up and down buttons. Each card has the name and description per language, the colour (labelled swatches, saying which track already uses a colour) and the icon. Built-ins keep theirs.
- Levels have a stepper (1–12) that can't go below the highest level units use, and optional level names. A "Hide from learners" switch hides a track.
- Delete is offered only for an added track that no unit uses.
- New tracks get an id suggested from the English name (`slugOf`), editable until the first save.
- "Save tracks" sends the whole list. Refusals are explained: someone saved meanwhile, or which units still use what changed.
- After a save, the provider switches to the new list at once (`apply`).

## Languages and right-to-left

- **UI strings:** `src/i18n/en.json` and `ar.json` ship with the app. `t(key, vars)` interpolates `{var}` and formats numbers with the language's numerals (Arabic-Indic for `ar`). A key a language lacks shows in English; in a right-to-left language that English is isolated left to right (LRI…PDI) so its punctuation stays at its end, and a lab (English and Arabic only) is laid out in English, left to right (`LabShell`). Course text that falls back to English is not isolated yet. `useI18n()` also gives `dir` and `locale` (for `Intl` dates and numbers). Their Arabic is friendly Modern Standard Arabic, like the course text (Egyptian is for the videos and the capstones' course text); `tests/i18n-plural.test.tsx` fails on Egyptian words in any Arabic UI dictionary.
- **Counted words:** a number `{n}` picks the string's plural form, `<key>.<category>` (`one`, `two`, `few`, `many`, `zero`: the language's `Intl.PluralRules`), when the dictionary has it; the key itself is the "other" form. So `kit.pages` is «صفحة واحدة», «صفحتان», «٣ صفحات», «١١ صفحة», and "1 page" in English. A language without the forms keeps its one string, and every key of `en.json` must also be in `ar.json`. Where a phrase would need forms on another variable, it says it as a label instead («عدد الكلمات: {n}», "Seats: {seats}").
- **Names inside sentences:** wrap user and organization names with `isolate()`, the plain-text `<bdi>`, so a Latin name can't reorder an Arabic sentence.
- **Arabic wording in courses:** `docs/curriculum/ar-lingo.md` is the glossary (one word per concept, the same in the Egyptian narration and the MSA course text) and the register rules. Apply a new term there first, then in the units and storyboards.
- **Separators:** never use "·" in Arabic text (it reads as Arabic zero). Use `t("common.sep")`, which is " · " in English and "، " in Arabic.
- **Codes, logins and URLs** always render left-to-right (`dir="ltr"`). Inputs use `dir="auto"`.
- **Code inside Arabic course text** (`[14, 74]`, `print("SENT")`, `{"day":"monday"}`, `=SUM(B2:B9)`, `V = I × R`, `θ = 3 − 0.1 × 6`) sits in invisible left-to-right isolates (U+2066 … U+2069), or it reads in the wrong order. They are stored in the unit files and the course packs (`content/packs`, printed in the course-pack PDF): `node scripts/isolate-code.mjs --fix [<unit>…]` works them out (`scripts/lib/isolates.mjs`; no ids: every unit and pack), and `tests/units.test.ts` fails on any string that `--fix` would change, on isolates that don't pair up, and on an isolate that holds a line break.
  - **Runs:** Latin words, numbers, formulas and operators joined by spaces, with quoted strings (spaces inside kept), `_`, `|`, `&`, `==`/`!=`/`>=`, an ellipsis (`k = 0 if ... else 1`, `UPDATE … SET`), and a sign, operator or `.` glued to a word (`=SUM`, `.get`, `−1`, `.venv\Scripts\activate`). After the first word an empty `()`, `[]` or `{}` continues the run, so `TOOLS.get(agent, [])` is one piece; so does a slice (`[::-1]`). After Arabic a run may open with `%`, `&`, `|`, `^` or `*` before code (`% len(route)`, `& 1`). A number joined to a word (`2-opt`, `24-hour`) needs one too: after Arabic it would show as "opt-2". So do numbers apart (program output `5 7` shows as "7 5"), a ! glued to a word (`n!`, `P@ssw0rd!`) and a Python header with its colon (`for i in range(6):`, `else:`; "mask: for …" is a word, then the header).
  - **Formulas:** Greek letters, combining marks (`x̄`, `p̂`), modifier letters and sub- and superscripts (`Aᵀy`, `Cᵢ`, `gᵃ`, `Σⱼ`, `n²`), primes (`s′`), norms (`‖w‖₁`) and the maths operators (`∂ ∇ ∑ √ ∞ ∈ ≡ ⋅`) are part of a run, so `∂L/∂w = 2(wx − y)x`, `P(60 < μ < 68) = 0.95` and `softmax(QKᵀ/√d)V` are one piece each. `√` only opens a word, so «√(١٠ × ٣٠)» stays Arabic maths; an Arabic-Indic number that ends a formula joins it (`k = ١`), one the formula goes on from leaves it right to left (`r = ١٧ ÷ √(…)`). `←` joins only letters (`θ ← (1 − 2η)θ`): «8 ← 4 ← 2» and «إيميل ← Continue» are Arabic prose.
  - **A named operator:** a comparison operator standing alone between Arabic words (`<`, `>`, `<=`, `>=`, `!=`, `<>`, `≤`, `≥`, `≠`), or after a proclitic, is a symbol being named and is mirrored right to left (≥ shows as ≤, `>=` as `=<`), so it gets its own isolate: «تشمل ⁦>=⁩ العدد»، «من نوع ⁦≥⁩ وكلفة»، «و⁦<⁩ لا يُبقي». Arabic maths with an operand (a number or a one-letter variable beside it, «س ≥ ٥»، «… ≥ ١٠٠», or glued, «≥٨٠٪») is meant to mirror and stays as it is.
  - **Never across:** a line break (on screen a line break ends every isolate, so one that spans lines scrambles both; a list's number stays outside: «4. ⁦Public → Create repository⁩»), or a sentence's end («⁦1/1 = 1⁩. ε الأصغر»).
  - **Left with the sentence:** ending punctuation, and brackets and quotes without a partner, as in «(… x = 1)»; a run ends before an opening bracket it doesn't close, so a citation reads «⁦NIST AI 100-2⁩ (Vassilev وآخرون، ٢٠٢٤)».
  - **Whole strings:** an Arabic field with no Arabic letters that holds code (an option such as `sum(marks) / len(marks)` or `29 / 32`) is isolated whole, line by line. Media paths and links are left alone.
  - **Whole lines:** inside Arabic text, a line with no Arabic letters that reads as code (it has a symbol such as `>`, `|`, `&` or `=`; a bare path or link doesn't count) gets one isolate for the whole line, so the symbols at its ends stay in place: a setup step's `ollama serve > /tmp/ollama.log 2>&1 &` (before, only `tmp/ollama.log 2>&1` was isolated and the `/` and `&` moved). A list's leading number stays outside, and trailing sentence punctuation is trimmed as for other runs. A plain line such as `ollama pull qwen2.5:1.5b` is left as it is. `tests/isolates.test.ts` ("a line of code inside Arabic text").
  - **Re-runs:** `--fix` works every string out afresh. It mends isolates that older rules put around half a piece of code (`θ ⁦= 3⁩`, `⁦k =⁩ ١`) or across a line break, and keeps hand-placed ones that don't overlap a new piece («⁦What is your PIN?⁩», `⁦( [ {⁩`, «⁦>=⁩»). First-strong (U+2068) and right-to-left (U+2067) isolates are never touched. Change the rules with a dry run first (`node scripts/isolate-code.mjs`, no `--fix`) and read every change.
  - **Answers:** the lesson engine drops isolates and direction marks before comparing a typed answer, and reads Arabic-Indic (٠–٩) and Persian (۰–۹) digits, ٫ ٬ and ٪ as 0–9 . , and %, in every UI language (`norm` in `lesson/engine.ts`; the code steps do the same in `code/harness.ts`).
- **Light lessons isolate their own text** (the vendored player; Lesson Studio `packages/player/src/bidi.ts`, also used by the iot and network packs): each left-to-right run in Arabic text goes in a `<bdi dir="ltr">`. A run starts with a Latin or Greek letter, a digit, ∂ or ∇ (or `(`, `÷`, `√` before one) and keeps accents, small letters and sub- and superscripts (`2θ = 6`, `∂L/∂a = 2`, `softmax(QKᵀ/√d)V`, `R̂`, `xₜ`); a full stop and a space end it (`= 3. ∂L/∂w`, `SQL. SELECT`) except after an abbreviation (`e.g. Python`); an assignment to a one-letter variable reads left to right (`θ ← θ − η∇R̂`), and other left arrows belong to the sentence (`8 ← 4 ← 2`). Until 2026-11-06 runs started only at a Latin letter or a digit, so formulas with Greek letters, ∂ or √ were split and reordered. The Arabic MP4s are drawn by the same player, so a rule change means rendering them again.

### Languages platform admins add

English and Arabic are built in (`BUILTIN_LANGUAGES` in `content/languages.ts`). Platform admins add more at `/super/languages`, with no deploy:
- **Add:** pick from common languages (names prefilled, direction from the code) or type a code. Each language has its own name, English name, writing direction and number locale, with a live sample.
- **Translate** (`/super/languages/:code`): one card per UI string with the English and Arabic for reference. Search; filters for "Not translated" and "To fix" (placeholders that differ from the English, which block publishing); a progress bar. Drafts are saved in `translations/{code}` with a `rev` check, by themselves as the course editor saves (`useAutosave`: 3 s after the last change, when the tab is hidden, and as the page closes, the app's own navigation included); Back saves first and asks inline only if that fails. No browser dialogs (the Tracks page asks inline too: its changes publish to phones, so they never save by themselves).
- **Spreadsheets:** download `.xlsx` or `.csv` (key, English, Arabic, the language), translate anywhere, import it back (`cms/sheets.ts`). The text column is the one headed with the code or name; empty cells are skipped, and keys the app doesn't have are reported and left out.
- **Publish** (`publishLanguage`): the page first saves the draft with only the keys the app has, trimmed; the function writes the immutable pack `content/i18n/{code}/v{n}.json` and lists the language in the settings. **Unpublish** takes it off the pickers. A draft can be deleted while unpublished.
- Only the main UI strings are translated: the course editor's own strings stay English and Arabic, and so do Labs and the landing page's marketing copy (they fall back to English).

**At run time** (`i18n/index.tsx`, `content/settings.tsx`):
- `SettingsProvider` reads the published languages with the tracks (`content/settings.json`) and registers them (`setLanguages`). `useLanguages()` feeds every picker: Onboarding, Me, the landing page (a menu once there are more than two), the lesson preview.
- **Packs load when someone picks the language**, never for everyone: cache-first by versioned path (`loadLanguagePack` in `load.ts`, a plain `fetch`, so guests still never load the SDK). Until it arrives, App shows its loading screen instead of a flash of English, for at most 6 seconds; after that English shows and the strings switch in when they come.
- The last version used is remembered (`darsi:langPacks` in localStorage), so the next start reads the pack from the cache at once instead of waiting for the settings over the network. A language that is no longer published shows English.
- **Direction has one source:** the language's `dir`. `applyLocale(lang, theme, dir)` sets `<html dir>`; before the settings arrive, `dirFor(code)` guesses from the code.
- **Fonts:** an added Latin-script language caches the Latin fonts plus the extended-Latin headings; an Arabic-script one (`fa`, `ur`, `ps`…) the Arabic fonts; other scripts use the phone's fonts (`familiesFor` in `platform/fonts.ts`). A language's own name in a picker always uses the phone's font (`.dr-lang-native`, `.dr-other-script`), so no page downloads a script's web fonts for one word.
- **Files:** built-in kits and media exist in English and Arabic only, so `kitUrl` and `videoSrc` use the English file for any other language (Hosting would otherwise answer a missing file with the app's HTML). `captionsFor` gives the language's captions, else the English ones. Read-aloud asks the phone for a voice in the language's own code.
- **Push:** a phone registers with its real language (`lang-<code>` topic). Notifications are worded in Arabic for Arabic and in English for every other language (see [Push notifications](#push-notifications)).

**Lessons in any language:** content is `LocalText` keyed by language code already. The lesson editor shows English plus the languages the author picks ("Languages" in the outline, remembered per browser; a unit's existing languages are always added). Every text, list, fill-in sentence, video, captions and kit file then has a field per language, in that language's direction. `validateUnit(u, { langs })` warns about missing translations (`missingLang`, with the language) for the shown languages, and the checks fold them into one group per language ("Français: 206 texts not translated").

## Design system and CSS

- **`@darsi/design-system`** turns `tokens.json` into CSS variables and TypeScript, and provides the components (buttons, fields, the question types, video player, lesson complete, classroom kit, and more), icons, logos and self-hosted fonts:
  - Baloo 2 / Baloo Bhaijaan 2 for display;
  - Noto Sans / Noto Sans Arabic for body text.

  There are two themes: the default light theme and **Sunlight**, a high-contrast theme for outdoor use. There is deliberately no dark mode. Reduced motion is handled globally.
- **App styles** live in `apps/web/src/styles/`, one file per area, and every class has exactly one owning file (`OWNERS` in `scripts/check-css.mjs`):
  - `base` (panels, tables, forms, pills), `layout` (rail, bottom nav), `auth` and `lesson` load globally;
  - `admin`, `person`, `people` and `landing` load with their lazy chunks;
  - `labs` (the catalogue) loads globally, and `lab-kit` (everything inside the lab apps, `lb-` classes) loads with the first lab.
- **`npm run lint:css`** enforces:
  - logical properties only (RTL);
  - design-token colours only, and every `var(--…)` must exist;
  - hard offset shadows only, with no blur or backdrop-filter;
  - no dark mode, letter-spacing or uppercase (both break Arabic);
  - nothing Chrome 87 WebViews lack: nesting, `:has()`, container queries, `@layer`;
  - no bare element selectors.
- **Breakpoints:** 600 px and 900 px only. Mobile-first. Tap targets are at least 48 px.

## Security

A static review on 2026-11-04 (3 High, 8 Medium, 12 Low) led to these changes. The report is in the session notes (`security-fixes.md`).

- **Who is who (H1):** a profile's `email` is the account's Auth email, set once. Admins find people through `findAccount` (Auth), see whether the email is verified, and are refused when several profiles claim one email. Sign-up by email sends a verification email.
- **Lesson results (H2, M1):** every progress field is typed and bounded; the summary trigger costs a fixed few reads per write and counts only published lessons, with the unit's own competencies.
- **Analytics (H3):** `collect` keeps counts only under known ids, drops events more than 10 minutes ahead and limits per address, device and instance. The analytics writes in the tutor's charge and in `recordPayment`/`recordRefund` never fail the call or the webhook.
- **Stale admin tokens (M2):** demotions and removals revoke sessions; privileged callables re-read the claims; nobody changes their own role.
- **Payments (M3, L7):** Paymob payments are matched by the signed order id; refunds only from signed or re-fetched data; a full refund takes back what it bought.
- **Passwords (M4, I1):** org admins reset only the logins the org made; `mustChangePassword` is cleared only after a real change.
- **Tutor credits (M5):** held before a call and settled after, a few calls at a time per person, `warm` limited.
- **Relay (M6, L9):** `ws` 8.22.0, an Origin header from Darsi's own site required, revoked tokens refused, sockets per instance and address capped (the address is the last `X-Forwarded-For` hop, the one Google's front end adds; the earlier ones are the caller's to make up), `/warm` limited.
- **Projects (M8, L2):** a field allow-list; attachments only from this project's Storage, in the person's own folder; no SVG or HTML; the app's file names. Review screens show only such links (`admin/evidence.ts`).
- **Smaller ones:** typed profile edits and CSV cells that can't run as formulas (L1); a transactional join limit (L4); framing, HSTS and opener headers (L5); transactional seats (L8); `tutorSearch` checks the caller first (L11); drafts can't be published or created across owners (L12).
- **2026-11 audit:** the org document holds nothing private (the request's contact and reason are in `private/request`), and org admins change only its name and logo (an unbounded `country` once pushed `stats/overview` past 1 MiB; `overview()` also cuts names and countries now). Element sizes are bounded too, not only counts: competency codes in lesson results (30 of up to 40 characters), track ids and level maps on profiles (`prefs` is gone), and `createdAt` at sign-up is the server's time. `collect` and `reportBug` key their per-address limits on the visitor's address behind Cloudflare (`cf-connecting-ip`, believed only when Hosting saw a Cloudflare edge: `clientIp.ts`), not on the edge every visitor of a city shares; `reportBug` counts toward its instance budget only reports that pass the address and account limits, so one address can't switch reports off for everyone. Username logins (`@users.darsi.app`) are only for accounts organizations make: one signed up for by hand gets no profile from the rules, `joinOrg`, `requestOrg` or the summary trigger (`handMadeUsername` in `roles.ts`); refusing the sign-up itself needs a blocking function (Identity Platform). A project is reviewed by the person's teacher and the admins of the organization the person is in now, the same people who can read it, not by the organization it was sent from.
- **Hosting headers:** every path gets HSTS. Every path except Firebase's own `/__/` pages (the sign-in helper frame and popup) gets `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `Cross-Origin-Opener-Policy: same-origin-allow-popups` (the Google popup still reports back), and a full `Content-Security-Policy-Report-Only`. That policy is only reported until it has been checked on the live site: the code sandbox's srcdoc frame inherits the page's policy, and the legacy build's inline scripts need hashes.
- **Left to do:** App Check on Firestore, Storage, the callables and `collect`; Auth's email-enumeration protection and a password policy; a dedicated service account for each server part instead of the default compute account (M7); signed certificates with a public check (M1); answer keys out of public Storage (I2); enforcing the CSP; npm advisories with no fix old enough yet (L10). Lesson results are still the phone's word for real lessons: someone can claim full marks for lessons they didn't do.

## Known gaps and roadmap

- **Videos** come from Lesson Studio (docs/CURRICULUM.md). Open there: its `convert.ts` knows only the 12 pack lessons' order, so newer videos end without a "Next: …" card; the students' videos use the narrator style written for teachers; arrow icons don't flip in Arabic; a seek past a quick check in the light player skips it (the MP4 player stops).
- **Security review:** the static review of the rules, functions and client was done on 2026-11-04 and the rules have their tests (see [Security](#security) and [Testing](#testing)). Left: a scan of the deployed site (`H:\htdocs\pentest-lab`), and the items under "Left to do" in [Security](#security).
- **Startup bundle:** eight files on 2026-11-07, against the four the bundle rule allows (see [Performance budget](#performance-budget)).
- **Content and languages:** the nine tracks, their code exercises and the students' courses fitted to school stages are in place; most primary and secondary courses are unpublished for now (51 of 96 live). Next: French, Swahili, Urdu and Hausa.
- **Certificates in the cloud:** cloud sync writes and reads `users/{uid}/certs` (see [Cloud sync](#cloud-sync)); the Firestore rules for it must be live before (or with) the app, or the reads and writes are refused (lessons still sync). Left: /super/certificates works from the summaries and the catalog, so it doesn't list a certificate whose course is unpublished; a person's page names such a course from its certificate only when it has lesson results to group (results from before `unitId` was recorded, in a course no longer offered, aren't grouped).
- **Native apps:** Android and iOS through Capacitor (see docs/NATIVE.md). The native shells don't register the web service worker, so they need native push (FCM through a Capacitor plugin) for reminders.
